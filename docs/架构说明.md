# 架构说明

从 PubMed 原始 XML 到一次带出处的回答，中间有九个环节。这里会说清楚**每一环做什么、
关键设计是什么、为什么这么设计**；那些反直觉的决定连同实测数字放在
[`工程笔记.md`](工程笔记.md)，此处只给指针，不重复。

```
PMC oa_comm XML
   │ ① 解析与切块
   ▼
9,243 万文本块 ──② 按块分层抽样 4.33% + 向量化──▶ Chroma 399.8 万 × 768
                └───────────────────▶ BM25 399.8 万块
                                          │
用户提问 ──③ 查询理解──▶ 增强查询 ──④ 多路召回 + 融合──▶ 候选池
                                          │
                                      ⑤ 多准则重排（+ landmark 保底）
                                          │
                                      ⑥ 上下文组装（[S#] 出处）
                                          │
                                      ⑦ 四段生成链
                                          │
                                      ⑧ 强约束层（提示 + 校验 + 修正）
                                          │
                                      ⑨ HTTP 服务（同步 / SSE 流式）
                                          ▼
                                    带出处、可溯源的回答
```

---

## ① 解析与切块

**语料**　PubMed PMC OA Bulk 的 **oa_comm 子集**（CC BY 等许可，允许商用），
快照 `oa_comm baseline 2026-06-18`，全量 11 包 PMC000–010，76 GB，4,000,645 篇。
格式是 JATS XML——结构化，带标题 / 摘要 / 分节 / PMCID，正是带引用溯源需要的东西。
下载：`scripts/下载数据.sh`，源站 `https://ftp.ncbi.nlm.nih.gov/pub/pmc/deprecated/oa_bulk/oa_comm/xml/`

**做什么**　把 76 GB JATS XML 解析成带元数据的文本块。
**产物**　9,243 万块（512 token / 64 overlap），平均 23.1 块/篇，11 个 parquet 分包。
**主模块**　`切块_主管线.py`

**关键设计**

- **结构感知，不是等长切割**。约 70% 的文章有 IMRaD 结构，切块时保住
  `abstract / introduction / methods / results / discussion` 的分节标签——
  后面的检索与上下文组装都会用到它（例如「这是方法学段落」这个信息，
  直接决定了它在证据里该不该被优先装）。
- **主键用 `pmcid` 不用 `pmid`**。`pmid` 在本语料不唯一（勘误记录与原文共用），
  首轮因此撞出约 70 篇 `doc_id` 冲突（[工程笔记 三·7](工程笔记.md)）。
- **自研 `smart_split`**。LangChain 的 `RecursiveCharacterTextSplitter` 在无换行的连续正文上
  overlap 会塌成 0，而医学全文里这种段落很常见。
- **按包流式处理**。9,243 万块不可能整体载入，切块与后续质量校验都是一次只读一个 parquet
  的必要列。

## ② 向量化与索引构建

**做什么**　从 9,243 万块里按**块**分层抽样 399.8 万，建向量库与稀疏索引两条召回腿。
⚠ 抽的是**块**不是篇：这 399.8 万块覆盖 227.4 万篇文献，平均每篇只有 1.76 块，**不是把 227 万篇整篇入库**。
**产物**　Chroma 集合 `medrag_bge_base`（3,998,000 × 768，余弦，65 GB）
+ BM25 索引（3,998,000 块，3.4 GB）
**主模块**　`向量化_建库.py`、`检索_构建BM25索引.py`

**关键设计**

- **规模由硬件实测容量定**，不是拍脑袋定的：400 万是 10 GB 显存 + 32 GB 内存下
  能建成、能查得动、且留出重排余量的规模。
- **嵌入约定必须全局统一**：CLS pooling + L2 归一化，**文档不加前缀、查询加指令前缀**。
  这套约定由 `BGEEmbedder` 独家承担，任何新建 collection 都必须复用它——
  换一个包装器就等于换一套约定，两个 collection 的余弦分**不再可比**，
  而多路融合正是拿它们直接比大小（[工程笔记 二·4](工程笔记.md)）。
- **BM25 用 `bm25s` 不用 `rank_bm25`**：后者全驻内存，400 万放不下；前者把分数预计算进
  scipy CSC 稀疏矩阵，可 mmap。
- **建库与查询共用同一套分词**（`检索_BM25公共.py`）。两侧分词不一致时不会报错，
  只是命中率莫名其妙地掉。
- **一份保险文件**：`merged_4m.parquet`（向量 + 正文 + 元数据合并表，15 GB）。
  它是阶段四向量库损坏后恢复出来的，也是此后一切重建的输入——
  重建库不需要重新嵌入，因此不吃 GPU。

⚠ **一个必须连口径一起给的事实**：抽样是**按块**做的，不是按文献。
落到文献层面，每篇平均只有 **1.76 块**在库（原文平均 28.64 块），**54.2% 的文献只有 1 块**。
所以「一篇文献在库里」不等于「它的关键段落可检索」。
这个事实解释了本项目的多处观测，详见 [工程笔记 三·13](工程笔记.md)。

## ③ 查询理解与增强

**做什么**　自然语言问题 → 结构化增强查询。
**主模块**　`检索_查询理解.py`

**关键设计**

- **中译英是必需项不是可选项**。索引是纯英文 `bge-base-en-v1.5`，直接用中文检索
  term-hit@10 只有 0.37，中译英后 0.97。
- **词典翻译有硬伤，整句 LLM 翻译才可靠**。词典是几百条的手写表，**词表外的中文字符
  整词丢弃**——一个词表外的病名会让整条查询退化成一两个泛词，检索结果完全跑偏，
  而且**响应体看起来和「库里真没有证据」一模一样**（[工程笔记 三·2](工程笔记.md)）。
  因此真正发出去的英文检索式会经 `retrieval_query` 回显给调用方。
- **同义词走 MeSH 而不是手写示例表**：`检索_构建同义词词典.py` 从 MeSH 2026 主题词表
  构建 9.5 MB 的词典。匹配时**按跨度长者优先裁决**——短正则会抢占更长的词典命中
  （`cancers?` 咬住 "cancer"，挡掉 "non-small cell lung cancer"）。
- **过滤条件必须落在语料真实取值上**，所以先有 `检索_扫描元数据分布.py` 扫一遍语料的
  年份、期刊、分节的实际分布，再决定能抽取哪些过滤条件。

## ④ 多路召回与融合

**做什么**　向量路与 BM25 路各自召回，融合成一个候选池。
**主模块**　`检索_多路检索.py`

**关键设计**

- **两条腿互补而非冗余**：BM25 能贡献向量 top-k 里没有的候选（验证里这是一条硬断言，
  必须确有独立召回才算通过）。
- **三种融合策略**（`simple` / `rrf` / `weighted`）可切换，默认 `rrf`。
  实测：给主查询降权对 RRF **完全没有影响**——`k=60` 时名次的作用压过权重。
- **向量路的过滤走后过滤，不走 Chroma 的 `where` 下推**：4M 集合上 `where` 会退化到
  约 108 秒，而「无过滤检索 + 过量取样 ×10 + Python 后过滤」实测 111.67 s → 0.027 s
  （[工程笔记 三·3](工程笔记.md)）。

## ⑤ 多准则重排

**做什么**　用 `bge-reranker-base` 交叉编码器给候选打相关性分，再综合时效性与权威性定序。
**主模块**　`检索_多路检索.py::MultiCriteriaReranker`

**关键设计**

- **相关性是主序，时效性只做同分裁决**。这是本项目最重要的一次检索侧修正：
  原先三项加权相加（0.60/0.25/0.15），实测**在净伤害检索**——整条流水线比它自己的
  向量腿还差。病根是「饱和型相关性分 + 线性年份分相加」这个结构，归一化修不好。
  改成「先按 ε=0.02 给相关性分档，同档内才比时效性」之后，T1 R@10 从 0.417 升到 0.497。
  完整机理、依据数字与措辞要点见 [工程笔记 二·1](工程笔记.md)。
- **排序键显式全序**：`round(rel/ε) → recency → fused_score → pmid → chunk_id`。
  同分裁决按构造大量并列，若靠稳定排序的副产品收尾，名次会**悄悄依赖上游融合顺序**。
- **候选池默认 50**。提大反而变差（R@10 随 50/100/200 单调下降 0.450/0.444/0.417）。
  但**诊断用途必须开到 200+**，否则分不清一篇文献是「没进候选池」还是「进了池被压下去」
  ——两个用途不合并成一个默认值（[工程笔记 二·2](工程笔记.md)）。
- **landmark 保底是有条件的**。10 篇关键 RCT / 指南存在一个独立 collection 里，
  在融合之后、重排之前并入候选；**只有当它的相关性分不低于将被它挤掉的那条时才补**。
  无条件保底等于往每个上下文里塞噪声——无关 query 上 landmark 的相关性只有 0.000~0.08，
  而被它挤掉的主库候选是 0.72~0.97（[工程笔记 二·7](工程笔记.md)）。

## ⑥ 上下文组装

**做什么**　候选 → 一段可直接塞进提示词的证据文本，每块带 `[S#]` 出处号。
**主模块**　`生成_上下文组装.py`

**关键设计**

- **token 预算是硬约束**，用从 Ollama GGUF 头部重建的 Qwen3 分词器精确计数
  （`生成_分词器.py`）。预算算错的后果不对称：算多了会被模型静默截断，
  而被截掉的正是最前面的 system 提示词和最相关的证据。
- **去重 + 来源多样性**：Jaccard 近重复丢弃，同一篇文献的多块有软惩罚与硬上限，
  避免一篇文章占满整个证据区。
- **筛掉证据后不重编 `[S#]` 号**：重编会让 `citations` 映射全部失效、复跑日志也对不上。
  代价只是编号可能不连续（`[S1][S3][S4]`），可接受。
- **按 `source_type` 保底**：landmark 来源在去重扫描时排最前、豁免相关性门槛、优先装，
  上限 2 条。

## ⑦ 四段医学生成链

**做什么**　证据 + 问题 → 带出处、经自我审查的回答。
**主模块**　`生成_流水线.py`、`生成_提示词模板.py`、`生成_LLM生成器.py`

```
①证据评估  →  按评估结果筛证据  →  ②生成草稿  →  ③批判审查  →  ④定稿
```

**关键设计**

- **四段各有独立的温度与输出长度**，且**每段可单独关掉**——关掉②③即退化为直接作答，
  这就是消融实验的开关（四段链是直接作答的 4.99× 耗时）。
- **`num_ctx` 必须显式设 12288**。Ollama 默认只有 4096 且**超长不报错**，
  它会静默丢掉最前面的内容，表现为「答得莫名其妙变差」（[工程笔记 三·4](工程笔记.md)）。
- **思考模式必须用 API 层的 `think:false` 关**，提示词里写 `/no_think` 关不掉；
  没关掉时思考段会吃光输出预算，表现为「模型不回答」（[工程笔记 三·5](工程笔记.md)）。
- **JSON 输出要容错解析**：`qwen3` 会在数值后多写一个引号（`{"relevance":3"}`），
  必须在括号平衡扫描**之前**用正则修掉，否则引号奇偶全乱、嵌套深度也跟着错。
  且温度 0 时原样重发无效——重试必须把上一次的具体报错回灌给模型。
- **引用编号由代码核对**，不靠模型自觉：`citation_check` 给出 used / available / fabricated，
  越界与编造的编号会被当场揪出来。

## ⑧ 强约束层

**做什么**　把「不许编、不许越界、必须给出处、格式要统一」从建议变成可判定的约束。
**主模块**　`约束_提示词层.py`、`约束_格式校验器.py`、`约束_受限流水线.py`

四层，各司其职：

| 层 | 内容 |
|---|---|
| A 硬约束提示 | 知识库边界、引用规则、禁止编造、术语与格式，写成指令语言而非散文 |
| B 阶段角色 | 四段链每段的角色与允许行为 |
| C 输出骨架 | 必需章节与固定结构 |
| D 生成后校验与修正 | 由代码判定合规性，能确定性修的就地修，修不了的交给模型修正轮 |

**关键设计**

- **提示词只能提高遵守率，判定必须由代码给**。层 D 检查引用编号范围、必需章节、
  缩写首次给全称、参考文献完整性、数字溯源、拒答三态。
- **拒答分三态**：完全拒答 / 部分作答 / 正常作答，**三态只看「核心答案」一节**。
  证据总结里的条数单独报，只在误拒判定里用——强约束本来就要求拒答时也列证据，
  拿它当「答了一部分」的信号会把 9 道应拒题里 8 道误标。
- **时间越界强制拒答**：问题问的年份晚于本次证据的最大年份时直接拒答。
  界限必须用**本次证据**的最大年份，用语料元数据里的 `pub_year.max`（2026）当界限，
  这一类根本判不出来。
- **判定与修正共用同一套归一函数**，否则会出现「校验说缺章节、修完还是缺」的死循环。
- **一处错误不污染两个指标**：越界编号只由幻觉类管，格式类只报「本来存在却没列进文献表」的编号。

代价是**上下文不是时间**：prompt token +40%，墙钟基本不变。

## ⑨ 服务化

**做什么**　把整条链包成 HTTP 服务，**不改动生成链与约束层的任何一行**——
埋点靠在外面包一层透明代理。
**主模块**　`服务_应用.py` 及 `服务_*.py` 共 13 个

**关键设计**

- **成功与失败同一形状**：泛型 `ResponseModel[T]`，21 个错误码分五族，
  四个全局异常处理器，未知异常一律归 5001 而不伪装成已知码。
- **两个探针分开**：`/health` 存活（不碰下游），`/health/ready` 就绪（探 Ollama 等 7 个组件）。
- **两种证据模式**：`snapshot`（固化的真实检索结果，秒级启动，不加载 65 GB 库）
  与 `live`（真检索）。
- **同步路由必须写成同步 `def`**。一次问答是 100 秒量级，写成 `async def` 会把事件循环钉死，
  连健康检查都不响应；FastAPI 会把同步路由丢进线程池，`request_id` 随 `contextvars` 复制过去
  （实测确认过）。
- **SSE 的失败只能在流内表达**。一旦开始 yield，状态行已发出，再也没法表达 HTTP 层的失败——
  所以并发闸门、鉴权、参数校验必须在返回流式响应**之前**做完。
  流式请求的耗时中间件也量不到（它在响应头发出那刻就停表），要由流生成器自己收尾时写。
- **文献元数据查询完全不走 Chroma**，走离线建的 SQLite 目录：Chroma 上第一次带过滤查询
  要 22 秒并把内存顶到 13.68 GB，会在第一次请求上撕掉 snapshot 模式的承诺
  （[工程笔记 二·3](工程笔记.md)）。
- **把系统已经知道的事说出来**：快照模式下问范围外的问题，服务端在选证据那一步（第 0 秒）
  就知道匹配不上，所以有 `/qa/topics` 让客户端先自检，而不是等整条链跑完二十多秒再拒答。

## 一条请求的完整时间构成（live 模式实测）

| 环节 | 耗时 |
|---|---|
| 检索器首次加载（每进程一次） | 约 67 秒 / 15.8 GB 内存 |
| 单次检索（含融合与重排） | 约 0.5 秒 |
| 中译英（LLM 整句） | 约 5 秒 |
| 四段生成链 | 约 30~40 秒 |
| **同步单轮合计** | **约 34~46 秒** |
| 流式：出处清单推给客户端 | **0.03 秒** |
| 流式：首个答案字 | 7.7~8.0 秒 |
