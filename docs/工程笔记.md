# 工程笔记

这里记录的是**做这个系统的过程中，靠实测换来的判断**：哪些环境约束不能违反、
哪些工程决策是怎么定下来的、哪些坑踩过一次就不该再踩第二次。

它和别的文档分工不同：

| 文档 | 回答的问题 |
|---|---|
| [`README.md`](../README.md) | 这是什么系统、怎么跑起来 |
| [`docs/架构说明.md`](架构说明.md) | 数据怎么流动、每一环做什么 |
| `任务N/README.md` | 第 N 阶段做了什么、量到了什么数 |
| **本文档** | **为什么是这么做的，以及做错过什么** |

三条使用约定：

- **每条都带依据数字**。没有实测支撑的判断不写进来。
- **被推翻的结论保留，并标明推翻它的证据**——一条曾经成立、后来被证伪的结论，
  比一条从未写下的结论更有用，它至少挡住了重复走一遍。
- 章节编号（`一·3`、`二·1`、`三·8`）是稳定锚点，代码注释里的交叉引用指向它们，
  重排顺序会让那些引用失效。

## 一 · 环境与运行铁律

这一节的每条都属于**违反了就一定失败**的类型，且失败形态往往不是报错，而是静默地
得到错误结果。

### 一·1 Python 解释器只能用 conda 环境里那个

`E:\rag\conda\envs\medrag\python.exe`。系统 PATH 上的 `python` 是 3.14，没有 torch /
langchain / chromadb。用错解释器的表现是 import 失败，属于少数会当场报错的一条。

环境是 conda-forge 的 Python 3.11（选 conda-forge 而非默认源，是为了规避商用授权限制）。

### 一·2 `HF_HOME` 必须在脚本开头硬覆盖

```python
os.environ["HF_HOME"] = r"E:\rag\hf-cache"
```

项目早期目录名是 `E:\medrag`，后来改成 `E:\rag`，但**用户级持久化的 `HF_HOME` 仍指向
旧路径**。不覆盖的话，离线加载 bge 三件套会失败。

### 一·3 起 Ollama 前设 `OLLAMA_MODELS`

`$env:OLLAMA_MODELS = "E:\rag\ollama\models"`，同 一·2 的历史原因。

### 一·4 `import pyarrow` 必须早于 `import torch`

Windows 上顺序反了会 DLL 冲突 → 段错误 exit 139。这条没有优雅的解释，只有实测结论。

### 一·5 输出编码

`PYTHONIOENCODING=utf-8`，否则中文输出乱码。

⚠ 这条管的是 **Python 的输出**。PowerShell 对**脚本源文件**的解码是另一件事，见 一·11。

### 一·6 中文文件名的模块按路径导入，且必须登记进 `sys.modules`

本项目的脚本文件名是中文，不能 `import 检索_多路检索`，只能：

```python
spec = importlib.util.spec_from_file_location(name, path)
mod  = importlib.util.module_from_spec(spec)
sys.modules[name] = mod          # ← 这一行不能省
spec.loader.exec_module(mod)
```

省掉登记那一行的后果不是导入失败，而是**同一个文件产出多个互不相等的模块对象**，
其中的类彼此 `isinstance` 判定必然为假。具体形态见 三·8。

### 一·7 验证脚本里每个 ✓/✗ 都必须由变量算出

阶段五出现过无条件 `print("...✓...")`——交付结论当时没有任何代码支撑。此后所有
`*_验证.py` 的每一条结论都由实际比对的变量决定，`judge()` / `check()` 这类辅助函数
统一收口。

### 一·8 每加一条断言，先问「功能完全失效时，它会不会照样绿」

一·7 只挡住了假检查，挡不住**空洞断言**——一条从未被触发的断言，和一条不存在的断言，
交付价值完全相同。这是本项目撞得最多的一族问题，六种形态与修法见 二·8 与 三·15。

写法：把「本次检验实际覆盖了多少样本 / 触发了多少次」算出来打进结果，
并让**它为 0 时判不通过**。

### 一·9 多小时任务在人自己的终端跑

建库、建索引这类几小时的任务不要交给会被回收的后台进程。阶段四因此把 Chroma 库
杀坏过一次（回收周期实测约 3.5–4.8 小时），后来靠 `merged_4m.parquet` 才恢复。

### 一·10 项目根由 `scripts/_medrag_root.py` 解析，不硬编码

解析顺序：`MEDRAG_ROOT` 环境变量 → 从 `__file__` 上溯找标志目录（同时含 `scripts/`
与 `requirements.txt`）→ 兜底 `E:\rag` 且仅当它真实存在。

⚠ **解析不出来时抛 `RuntimeError`，不返回一个不存在的路径**。指向不存在目录的路径
不会报错：Chroma 会当场建一个空库、BM25 缺失只把那一路静默关掉，最终表现成
「库里没有证据」——一个和真实召回失败长得一模一样的假象。

⚠ 这个模块名用 ASCII：它被 57 个脚本 import，如果它自己也是中文名，就得先解决
一·6 那个问题才能加载它。

### 一·11 PowerShell 相关的两条

- **含中文的 `.ps1` 必须存成 UTF-8 with BOM**。没有 BOM 时 Windows PowerShell 5.1 按
  系统 ANSI（GBK）解码，中文变乱码，而且**乱码字节会连带把语法读坏**——报的是
  `Missing expression after ','`、`The hash literal was incomplete`，一路指向根本没错的行。
- **`curl.exe` 传 JSON 请求体只有 `-d "@文件"` 可靠**。三种内联写法（单引号包双引号、
  `\"` 转义、`--%` 停止解析）全部失败，服务端返 `1004 请求体格式错误`；
  `Invoke-RestMethod` 能通但即使显式 UTF8 编码也把中文写成乱码。

  ⚠ 反过来，**部分 `.py` 带 BOM**（`golden_跑测.py` 就是）：Python 的导入机制认得，
  但 `ast.parse` / `compile` 会报 `invalid non-printable character U+FEFF`。
  批量改写 `.py` 的工具一律按 `utf-8-sig` 读、按原样写回，不能顺手抹掉别人的 BOM。

## 二 · 工程决策记录

每条的形式是：**现象 → 根因 → 决定 → 依据数字**。

### 二·1 多准则重排：recency 从加权项改为同分裁决

**现象**　多准则重排在**净伤害**检索。用 golden 检索评测集（235 条 query）做单路对照：
向量-only `R@10=0.490 / MRR=0.349`，而完整的融合 + 重排是 `R@10=0.417 / MRR=0.231`——
**全流水线比它自己的向量腿还差**。逐条数救毁：毁 26 条、救 15 条、净 −11。
被毁的 26 条里 13 条发表于 ≤2015；被救的 16 条**一条 ≤2015 都没有**。
典型个例：相关性满分（rel=1.00）的 2014 年文献从 `vec#2` 掉到 `final#73`。

**根因**　不是归一化 bug，重新标度修不好。病根是「**饱和型相关性分 + 线性年份分相加**」
这个结构本身：交叉编码器认可的候选，rel 全挤在 1.0 附近，池内前 20 的 rel 标准差只剩
约 0.08，而它们的发表年份铺得很开，recency 标准差约 0.18（2.2 倍）。
于是在默认权重 0.60/0.25/0.15 下，**recency 的实际排序影响力几乎等于 rel（44.0% vs 47.7%）**。
实测「池内 min-max 归一后再加权」得到 MRR=0.207，比不归一的 0.231 **更差**——
归一化把 recency 的跨度拉满到 [0,1]，反而更压得过 rel。

**决定**　recency 不再进加权和，改为**同分裁决**：先按 ε 把 rel 分档，同档内才比 recency。
默认 `rerank_mode="tiebreak"`、`ε=0.02`。旧行为保留为 `--rerank-mode weighted`，随时可跑回来对照。

**依据数字**　真跑 235 条：配置 wide 下 T1 `R@10 0.417→0.497`、`MRR 0.231→0.306`；
线上默认配置 prod 下 `R@10 0.450→0.483`、`MRR 0.266→0.331`。
按发表年份分桶：≤2015 **+22.5pp**、2016–19 +6.6pp、2020–22 持平、2023+ +2.4pp——
精确表述是「**没有一格更差、三格严格更好**」，不是「四格全部更好」。

选 ε=0.02 而不是 0.01，是因为**它是唯一在 2023+ 那一格也严格更好的**（0.476 > 0.452，
ε=0.01 在那格只持平），而 2023+ 正是 recency 应当发挥作用的地方。
ε 在 0.005~0.05 之间是**平台不是刀刃**（R@10 只差 2pp）。

**措辞上的要害**：这不是「recency 无价值」，而是「40% 的加法权重代价过高——
用新文献 +2.3pp 换老文献 −30pp」。收益来自**把 recency 从加法项移除**；
同分裁决是在此基础上以可控的小代价保留 recency 的原意。
实测每一档 ε 的 MRR 都低于纯相关性排序（0.357），即**同分裁决相对纯相关性是净支出**。
它买到的是 benchmark 测不到的临床时效价值（「同等相关时新指南优于旧指南」），
而 golden 集的 ground truth 由文本定义，测不出那个。

**附带的排序契约**　同分裁决按构造会产生大量并列，所以排序键必须**显式全序**：
`round(rel/ε) → recency → fused_score → pmid → chunk_id`。若靠稳定排序的副产品收尾，
名次会**悄悄依赖上游融合顺序**（加 landmark 路、改融合权重都会让它无声变化）。
末级用 `chunk_id` 不能止于 `pmid`——`pmid` 在本语料不唯一（三·7）。

**回归硬断言**　改完之后，新代码的 `weighted` 模式**逐位复现**老代码的原始基线：
逐条名次 235/235 × 2 配置 × 2 粒度全同，聚合指标与四个年份桶逐位相同（14 项断言全过）。
所以这次改动**之前那批历史对照数字仍然有效**。
这条值得当模板：**改排序路径后，旧模式必须能逐位复现旧数字，否则历史数字全部作废。**

### 二·2 `rerank_pool` 生产默认值维持 50，诊断用途开到 200+

**现象**　把重排候选池提大反而变差。T1 主指标 R@10 随池子：50 → **0.450**、
100 → 0.444、200 → 0.417，**单调下降**。

**根因**　池子越大，重排把「不相关但新且权威」的文献捞上来的机会也越多。
早期观察到的「融合第 58、60 名重排后能进前 10」**现象是真的**（本轮约 4.6% 属此类，
最夸张的一条 `fused#172 → final#2`），但那是个案收益，**净效果为负**。

**决定**　两个用途分开，不合并成一个默认值：

- **生产默认 50**。
- **诊断必须开到 200+**：要查一篇文献是「不在候选池」还是「进了池被压下去」，
  小池子根本分不开这两种情况，只有 `search(dump=...)` 导出的 `fused_rank` / `final_rank`
  才分得开。

**依据数字**　golden 235 条实测，见上。这条推翻了更早一次基于个案观察的推论——
个案收益与净效果是两个问题。

### 二·3 文献目录走离线 SQLite（源是 parquet），不走 Chroma

**现象**　面向请求的文献元数据查询，如果落在 Chroma 上：
`count(distinct pmcid)` 要 **221.2 秒**，`count(*)` 25.2 秒，
而**第一次** `get(where=…)` 要 **22 秒并把进程 RSS 顶到 13.68 GB**。

**根因**　之后每次 `get(where=…)` 只要 0.44 秒——所以只测第二次会得出「很便宜」的
错误结论。真正的代价全在第一次。

**决定**　离线建一份 SQLite 目录（`服务_文档目录.py --build`，45 秒，1.0 GB），
运行期完全不碰 Chroma。那 13.68 GB 会在**第一次请求**上撕掉 snapshot 模式
「不加载 65GB 库」的承诺，而且表现得最像 bug。

**依据数字**　建成后：详情 0.0 ms、列表 0~1 ms、标题模糊搜最坏 824 ms。
快路（读 parquet 一列，0.7 秒）与慢路（Chroma，221 秒）**结果逐位相同**，两边都真跑过。

**两个连带结论**：

- **建目录必须用 `merged_4m.parquet`（3,998,000 行），不能用 `subset_4000000_s42.parquet`
  （4,002,283 行）**。后者多 4,283 块 / **2,329 篇**，会凭空多出两千多篇「查得到、
  检索不到」的幽灵文献，而 `3001 文档不存在` 这个错误码本该是准的。
  两个文件的 distinct pmcid 分别是 2,274,167 与 2,276,496，**前者与 Chroma 那趟 221 秒的
  结果逐位相同**（真跑过，不是推断）。
- **`LIKE '%kw%'` 的基准必须量最坏一档**。`... WHERE title LIKE ? ORDER BY pmcid LIMIT 21`
  在命中多时凑够 21 条就停：`%CRISPR%` **6.0 ms**、命中少的 `%Fabry disease%` 57.3 ms、
  **零命中时全表扫 824.2 ms**（带 COUNT 则 1.5 s）。只量第一档会得出「快 130 倍」的
  错误结论。量到最坏一档之后，才敢下「不上 FTS5」的结论。

### 二·4 新建任何 collection，一律复用 `向量化_建库.py::BGEEmbedder`

**现象**（差点发生，在建 landmark 集合时拦下）　chromadb 自带的
`SentenceTransformerEmbeddingFunction` 用起来更省事。

**根因**　主库的约定是 **CLS pooling + L2 归一化**，**文档不加前缀、查询加 `QUERY_INSTRUCTION`**；
检索侧自己算好 query 向量再传 `query_embeddings=`，**collection 上不挂 embedding_function**。
换一个包装器就等于换一套池化 / 归一化约定，两个 collection 的余弦分**不再可比**——
而多路融合正是拿它们直接比大小。

**决定**　文档走 `embed_documents`（不加前缀）、查询走 `embed_query`（自动加前缀），
建 collection 时**只传 `embeddings=`，不传 embedding_function**。
检索侧已含前缀的向量查询直接走 `_encode`，不能再调 `embed_query`（会二次加前缀）。

**为什么值得单列一条**　这类错**不抛异常、不报警、不体现在任何断言上**——
库建得成、查得动、分数看着也正常，只是排序**悄悄失去意义**。
等发现时，往往已经在它上面做了一堆调参和结论。

### 二·5 字段名必须承诺它真实的语义

**现象**　`landmark_构建集合.py` 里 `extract_fields()` 曾把 METHODS **整段原文**塞进一个
叫 `population` 的字段。后来加人群标签时写 `entry = {..., "population": 人群标签, **ext}`，
`ext["population"]` **静默覆盖**了它——于是被向量化的锚点行变成了一整段方法学正文。
没有异常、没有告警，只有检索效果莫名其妙。

**根因**　字段名撒了谎，而调用方（包括写它的人）会按名字去用它。

**决定**　如实改名 `methods_text` / `results_text` / `conclusion_text`。

**为什么和 二·4 是同一类**　都是「**约定被悄悄换掉、系统照常运行、不抛任何异常**，
只有结果慢慢变得没道理」。这类问题靠测试很难抓（每一步单看都对），
只能靠**命名不撒谎**在源头堵住。

### 二·6 抬分类改动的对照组是「该抬的 vs 不该抬的」，不是「改前 vs 改后」

**现象**　修一篇该召回却没召回的 landmark 文献时，两个候选改法在**目标文献单条上**
是这样：

| HFpEF 题面 | 现状 | 别名前置 | 人群前置 |
|---|---|---|---|
| EMPEROR-Preserved（**该抬**） | 0.6117 | **0.8603** | 0.8307 |
| DAPA-HF（**不该抬**，HFrEF） | 0.3965 | **0.7446** | 0.4399 |
| EMPEROR-Reduced（**不该抬**，HFrEF） | 0.6869 | **0.8872** | 0.6380 |

只看第一行会选「别名前置」（0.8603 > 0.8307）。

**根因**　别名前置把两个**错人群**的试验一起抬起来了，而那两个正是这套评测里
「张冠李戴」的源头——等于一边修漏检、一边给串位铺路。

**决定**　选人群前置。**一个把正确答案和错误答案一起抬起来的改法不是改法。**

**依据数字**　人群前置在整体代价上也更小：golden T1·prod·MRR 的损失从 −0.00116 降到
**−0.000005**（1/232），ground truth 名次变化从 24 处降到 **6 处**，R@k 一位不变。

**通用形式**　抬分类改动的对照组**不是「改前 vs 改后」，而是「该抬的 vs 不该抬的」**。
只有前者的单条对照会得出**反向**结论。这类实验很便宜（只用重排器、不加载 65GB 库、秒级）。

### 二·7 「保底配额」必须是有条件的

**现象**　P0 的原方案写「landmark 保底 2 条」。按字面实现就是无条件塞进最终结果，
在 golden 上一跑就露馅：那 10 篇是心内科试验，绝大多数 query 与它们无关——
**无关 query 上 landmark 的交叉编码器 rel 只有 0.000~0.08，而被它挤掉的主库候选是 0.72~0.97**。
等于在一个答错要出人命的场景里，白占 2/10 的证据位放噪声。

**根因**　保底规则没有贴着它要修的机理写。要修的不是「不相关也该有位置」，
而是「同分裁决按 ε 分档后档内比 recency，2014–2021 的老文献输给 2023 的新综述」（二·1 量到过）。

**决定**　判据贴着机理：**只有当 landmark 的 rel ≥ 将被它挤掉的那条（容差 = 重排的 ε）时才补**。
自校准、不用手调阈值、不随语料漂移。并且把「被这条规则挡下多少条」返回出来
（`search()` 的 `landmark.rejected`）——**它恒为 0 就说明保底又退回成无条件了**，
是一条会自己报警的断言。

**依据数字**　两把尺子各量一半：
收益侧（landmark 探针，8 道题面）期望的 landmark 进上下文 **8/8**，进的那一块带要害数字 **13/14**；
代价侧（golden 235 条）**R@5/R@10/R@20 一位不变**，T1·prod·MRR −0.000005，ground truth 掉出 top10 **0 条**。

⚠ **golden 只量得到代价，量不到收益**——它的 ground truth 全部抽自主库，
landmark 在它上面只可能挤位置。只跑一把尺子会得出片面结论。

### 二·8 报告防降级判据按「证据种类」比，不按标量比

**现象**　报告是交付材料，被弱运行覆盖是纯损失且不可逆。同一个坑变形了六次：

| # | 形态 | 判据当时的样子 | 怎么被打穿的 |
|---|---|---|---|
| ① | 按时间 | 「更新的覆盖旧的」 | **更新不等于更全**（靠另存救回） |
| ② | 改成按项数 | 新报告项数 < 旧报告则拒写 | —— |
| ③ | 项数被绕过 | 只比项数 | 离线做到 224 项 > 「离线 160 + 实测 5 = 165」，**5 项 live 端到端照样没了** |
| ④ | 项数被绕过（同数） | 只比项数 | 25/25 vs 25/25，但一份跑的是 **4M BM25 索引**、另一份是 **500k 子集** |
| ⑤ | 脚本压根没有判据 | 无 | 一次离线 58 项的运行**静默覆盖**了 65 项的 `--live` 版 |
| ⑥ | 判据放错位置 | 有判据但在末尾 | 脚本在 import 阶段就 `open(..., "w")`，**文件在第一条断言跑之前已被清空** |

**根因**　**强弱不是一个标量**。数量与时间都是标量，而「这一轮跑的是哪一类证据」不是。

**决定**　判据要问「**新的是否包含旧的每一类证据**」，不是「新的是不是更大」。
现在的实现两条并列：项数不得减少 **且** 旧报告有 live 实测时新报告也必须有。
形态 ⑥ 的修法是把报告先攒在内存里、跑完再决定落不落盘——顺带好处是中途崩溃时
旧报告原样保留，而不是留下一份被截断的残报告。

**依据数字**　`服务_验证.py` 离线 224 项 / 带 `--live` 229 项（live 独占 5 项）；
`生成_上下文组装_验证.py` 离线 58 项 / 带 `--ollama` 61 项 / 再带 `--live` 65 项（live 独占 4 项）。
两处都实测过：弱轮被拒绝时目标文件 MD5 逐位未变。

⚠ **形态 ⑦ 一定还会出现**。加新判据时按「证据种类」这个方向加，别再加一个标量。
⚠ 这个坑**跟着报告文件走，不跟着脚本走**——每个会写交付报告的脚本都需要同一道闸门。
目前装了判据的是 `服务_验证.py`、`生成_上下文组装_验证.py`、`检索_多路检索_验证.py`；
其中第三个的第二条判据不是项数而是**BM25 语料规模**（500,248 块 vs 3,998,000 块，两轮都是 25/25，项数完全看不见这个差别）。

### 二·9 评测集的 held-out 纪律

**现象**　两批评测材料已进公开仓库：235 条检索评测 query 与 ground truth；
5 道临床评测题**连同参考答案、PMID、精确统计量、扣分触发词**写在同一份被提交的文档里。

**根因**　推上去那一刻起，题目、答案、评分口径都可能已被抓取、缓存、索引。
**删掉也没用**——这是不可逆的。

**决定**　两批**永久降级为回归集**：

- ✅ 只用来确认改动没造成退化——「改一处 → 回测一次，看有没有变差」
- ❌ 不能用作「能力提升了多少」的验收依据
- 汇报措辞：说「回归通过」，不说「达到 X 分」

**新出验收集的三条硬要求（缺一条等于没做）**：

1. **不进仓库**——放已被忽略的目录或仓库外
2. **参考答案与评分细则不落盘到任何被提交的文件**——包括 README、任务书、报告正文、
   脚本里的常量。上面那 5 道题栽的正是这条：题目本身尚可，但答案和它写在同一份文件里
3. **在 `.gitignore` 里显式列出文件名**——不能靠「记得别 `git add`」来保密

### 二·10 landmark 集合的联网边界

**现象**　主库来自 PMC oa_comm 开放子集，10 篇心内科关键 RCT / 指南**一篇都不在其中**
（逐篇查证，全部属于「不在 oa_comm」这一类，而非「在库但没被抽中」）。

**决定**　**构建期一次性联网**取这 10 个 PMID 的摘要（1 次请求，0.5 秒），**运行期仍全离线**。
条目落盘之后重建 collection 不需要再联网，**跑服务的人永远不需要联网**。
发出去的只有 PMID，没有任何本机数据。取回的摘要正文不进公开仓库（版权归出版方），
只有种子清单（纯 PMID）进。

⚠ 这条不等于「本项目已不再全离线」——那是两回事。

**连带的查证结论**　语料不是「完全缺失」，而是「**沾边的在、要害的不在**」，
这比完全没有更麻烦：库里有这些试验的**次要分析**（PARAGON-HF 的糖代谢次要分析、
DAPA-HF 的四篇相关分析、DELIVER 的 improved-EF 亚组都在），**但每篇只有 1~4 块在库**，
主要终点的 HR / 95%CI / 入组人数大概率不在那几块里。

危险就在这里：完全没有证据时模型会拒答（强约束层管得住）；
而**有一堆沾边的文献时，模型会以为自己有依据**，于是从综述转述、次要终点、
隔壁人群的数字里凑一个出来——**有出处、可溯源、完全合规，但数字是错的**。

由此定下的验收判据：不是「有没有召回相关文献」，而是
**「引用的那一块原文里，主要终点的 HR、95%CI、入组人数在不在」**。
只看召回率会让这类改动得出一个成功的假结论——召回上去了，数字照样错。

⚠ 查证时**不要用试验缩写做匹配，只用 PMID**：`TOPCAT` 会撞上一个妇科肿瘤试验，
`ASCEND` 会撞一堆 ascending aorta。

## 三 · 已知坑与已被证伪的假设

### 三·1 温度 0 不可复现——方差在生成侧，检索侧已排除

同一份代码、同一份证据、`temperature=0` 连跑两轮 19 题，**9 道应拒题里 3 道的拒答形态
翻转**，两轮之间没有改动这几道的提示词。

**推论**：这个系统的**任何单轮生成侧评测数字都带未量化的方差**，包括历史报告里的全部数字。

**已缩小的范围**：golden 检索评测证明**检索侧是完全确定性的**——同一份翻译缓存跑三轮，
`rel_score` **47,400/47,400 逐位相同**，逐条名次也全同。所以方差**只可能来自生成侧**
（并发批处理 / 校验修正轮 / Ollama），检索层可以排除。

**操作含义**：需要一把无方差的尺子时用 golden 集，不用生成侧指标。
在方差来源定位之前，「多跑三轮取平均」不解决问题——三轮只会得到三个都落在噪声里的数。

⚠ 一个具体表现：两次检索的中译英给出 `primary endpoints` / `main endpoints` 两种译法，
相关性分随之变化——**检索层确定，但它前面那层翻译不确定**。
golden 集把翻译结果冻结成缓存，理由就在这。

### 三·2 中文查询必须先中译英，且不能走词典

索引是纯英文 `bge-base-en-v1.5`，直接用中文检索 term-hit@10 只有 0.37（会命中太极治抑郁、
中文标题文献之类），中译英后 0.97。

**更贵的一层**：默认的中译英走一份几百条的手写词典，**词表外的中文字符直接丢弃**。
「法布里病有哪些酶替代治疗药物」只命中「治疗」→ 剩一个 `treatment` 去查全库 399.8 万块 →
**检索回来的是蝴蝶名录和 1919 年的文章** → 一句「根据现有文献无法回答」。
库里明明有 Fabry 文献。换整句 LLM 翻译后，同一题答出 agalsidase alfa/beta + migalastat。

⚠ **这类错最贵：它和「库里真没有证据」在响应体里长得一模一样**，从答案上分辨不出来。
所以真正发出去的英文检索式现在会回显给调用方。

### 三·3 Chroma 的 `where` 下推在 4M 集合上退化

无过滤检索 1.2 ms，带 `where` 退化到 ~108 s。向量路默认走
`vector_filter_mode='postfilter'`（无过滤检索 + 过量取样 ×10 + Python 后过滤），
实测 111.67 s → 0.027 s。只有高选择性过滤才用 `'where'` 这个逃生阀。

（面向请求的**元数据**查询则完全不走 Chroma，见 二·3。）

### 三·4 Ollama 的 `num_ctx` 默认只有 4096，且超长不报错

`/api/ps` 实测确认。超长时它**静默丢掉最前面的内容**——正是 system 提示词和最相关的证据，
表现为「答得莫名其妙变差」。四段生成链必须显式设 `num_ctx=12288`（实测显存 6.33 GB，
10 GB 卡有余量）。

另：`num_predict=0` 会让 `/api/generate` 挂住不返回；要算 prompt token 数就传
`num_predict=1` 再读 `prompt_eval_count`。

### 三·5 qwen3 的思考模式只能用 API 层的 `think: false` 关

提示词里写 `/no_think` 关不掉。Ollama ≥0.9 把推理过程放进 `message.thinking`，
`content` 要等思考结束才开始写——思考段会吃光整个 `num_predict`，
结果是 **`content` 全空、`done_reason=length`、token 却烧了一堆**，看起来像「模型不回答」。
判断依据：`message.thinking` 非空而 `content` 为空。

### 三·6 qwen3 写 JSON 时会在数值后多一个引号

`{"relevance":3"}`，是本项目见过最高频的畸形（4 道验收题里 2 道中招）。
危害不止这一处解析失败：多出的引号把后面整段变成字符串，引号奇偶全乱，
平衡扫描算出的嵌套深度也跟着错。**必须在扫描之前用正则修掉**。

⚠ 配套的一条：**温度 0 时，JSON 解析失败后原样重发是无效动作**——输出逐字相同（实测）。
重试必须改变输入，做法是把上一次的具体报错回灌给模型。

### 三·7 `pmid` 并不唯一

勘误记录与原文共用 pmid（约 70 篇 doc_id 因此冲突过）。主键一律用 100% 完整且唯一的
`pmcid`。这条直接影响排序全序键的末级选择，见 二·1。

### 三·8 跨模块 `isinstance` 必然失败，异常处理器会静默失配

`module_from_spec` + `exec_module` 每调一次产出一个**新模块对象**，里面的类彼此不相等。

最贵的一次形态在服务层：五个模块都要 import 错误码模块，不登记 `sys.modules` 的话，
`raise SessionNotFound(...)`（B 副本）与 `@app.exception_handler(APIError)`（A 副本）
不在同一棵继承树上，FastAPI 按 MRO 找不到处理器 → 掉进兜底 →
**3002 / 4004 全部退化成 5001 / 500**，而且响应体看起来完全正常、不报任何错。

发现它的是验证脚本的接口组——手工点交互式文档永远发现不了。修法见 一·6。

跨模块传对象时的一般做法：按 duck typing 判，不用 `isinstance`。

### 三·9 `rouge` 库的三个坑

（rouge 1.0.1，全都撞过）

1. **它按空白切词**，一整句中文会被切成 1 个「词」——两句高度相似的中文 ROUGE-L
   实测 `0.0000`，按「中文按字 / 英文按词」预分词后 `0.7907`。
2. **它把 `.` 当句子分隔符**，而医学答案满是 `0.45`、`p<0.001`——小数点会把一句劈成两「句」。
   token 内的点要换成别的字符，`.` 只留作真句子边界。
3. **它的 LCS 回溯是递归的**，整段当一个句子喂进去，2000+ token 的真实答案直接
   `RecursionError`。给它真正的句子边界即可（这本来就是 ROUGE-L summary level 的正确用法）。

### 三·10 跨语种的关键信息比对必须走概念表

证据是英文、答案常是中文，「不良反应」与 `adverse events` 字面无交集，
安全 / 建议 / 机制三类召回率会**恒等于 0**——那不是模型漏了，是尺子坏了。

### 三·11 定义了 `__len__` 的对象不能用 `x or 默认值`

空容器布尔值为 `False`，`or` 会**悄悄丢掉**传进来的对象并新建一个。
生成缓存的包装器踩过：它照样能命中（用的是自己新建的那个缓存），
但调用方设的 TTL / 容量 / 温度门限全部失效、统计恒为 0。

写 `x if x is not None else 默认值`，并给这类对象加 `__bool__` 恒真。

**发现方式**值得记一笔：判定打印出「写入 0 条却因高温跳过 16 次」——
同一个对象上这两个数不可能同时成立。

### 三·12 `Enum.__hash__` 按成员名算，`3001 in set(ErrorCode)` 恒为假

整数与枚举成员的哈希不同，集合判定永远不成立——登记过的错误码也会被当成「未登记」。
用 `try: ErrorCode(x) / except ValueError`。

### 三·13 4M 是按「块」抽样的，不是按文献

每篇平均只有 **1.76 块**在库，而原文平均 **28.6 块**。实测分布：
**54.2%** 的文献只有 1 块进了库、覆盖率中位数 **5.9%**、完整入库 **0.6%**、有摘要块的 **7.7%**。

这是个**贯穿性解释因子**——凡是把「库里有 227 万篇文献」当前提的推理，都要先过这一关。
它解释三处：

1. 查某篇文献「在不在库里」是**三分不是二分**：不在 oa_comm ／ 在库但关键段落那一块
   没被抽中 ／ 被抽中了但排不上去。**一篇文献进了库不等于它的关键段落可检索。**
2. 任何「库里有 N 篇文献」的说法都要连口径一起给，所以文档接口同时给
   `total_chunks` 与 `indexed_chunks`，`abstract` 标为可选并写明填充率。
3. 一次问答拿到的通常是某篇文献的 1~2 块，很可能不含人群 / 终点定义那几段。
   「HFrEF 数据用来答 HFpEF」这类错，**有一部分可能不是模型不看，是上下文里根本没有**。
   ⚠ 这是**待验假设不是结论**。

⚠⚠ **但它不解释 golden 评测的任何一个数**。golden 的 ground truth 是从建库输入表
（`merged_4m.parquet`）抽的——「它有的 = 库里有的」——所以**每一条 ground truth
按构造都在库里**。因此 T1 那 27.8%「连 200 条候选池也没捞到」是**真·检索没捞到**，
不是没抽进库。**同一个事实，在一处是解释，在另一处是不成立的解释，必须分开记。**

### 三·14 methods / results 段几乎检索不到，且是两个问题叠加

methods 段 `R@5 = R@10 = R@20 = 0.182`——三个数完全相等，意味着 5~20 名之间一条都没多找到。
拆开看：**约四成五根本没进候选池**（200 条也没捞到）＝召回问题；
进了池的里面又有大半排在 20 名开外＝排序问题。BM25 对 methods 段尤其无力，
命中数只有 abstract 段的三分之一。

**原因**：方法学段落写的是通用流程语言（「患者被随机分组」「通过伦理审查」），
和「这研究怎么做的」既不词面重合也不语义贴近；同篇的**摘要块**反而更容易命中——
这也是文献级指标始终高于块级的主因。

⚠ 这属**切块策略**问题，超出重排范围，在重排层面找补是找错了地方。

### 三·15 检查器自己开的后门，恰好通向要查的东西

交付包校验里有一项「文档引用的文件必须在包内」。它的实现里有一行
`if base.endswith(".md"): continue`——本意是放过跨阶段互引（「见 任务6/README.md」这类）。

后果是：**所有对 `.md` 文件的引用都不检查**，包括几十处指向一份从不进仓库的文件的引用。
对拿到仓库的人来说那些全是悬空引用，而校验器**每次都打绿灯**。

**这和空洞断言（一·8）同源**：判据存在，但对特定输入永远不触发。
差别只在于，空洞断言是「条件太宽，永远为真」，而这里是「显式豁免，永远不看」——
**后者更隐蔽，因为豁免通常写得有理有据**。

**修法**：把豁免收窄到它真正要放过的那一类（跨阶段互引），
其余 `.md` 引用改为「必须是仓库里跟踪的文件」。

**已落地**：`校验交付包.py::check_dangling_docs()`——扫所有 git 已跟踪的文本文件，
凡是提到「本机有、但 git 没跟踪」的文档就判失败。它自报覆盖面
（本轮：扫 298 个已跟踪文件 × 比对 3 份未进仓库的文档），**任一数为 0 即判不通过**，
免得它哪天悄悄退化成一条永远为真的断言。上线当天就抓到两处存量悬空引用，
以及**它自己说明注释里那处**——写注释时点了那个文件名，被自己抓个正着。

### 三·16 拿终态判据去量中间态，测出来的是判据的错配

判据都是**针对某个特定状态**定义的，用在别的状态上，红的是判据不是系统。

现有系统的三处形态：

- **验证夹具要分两套**：把「元数据本来就残缺」的样本混进「合规基线」夹具，
  所有应当合规的断言集体失败——测出来的是夹具的问题。
- **拒答三态只看「核心答案」一节**：证据总结里出现带出处的句子是合规行为
  （强约束要求拒答时也列证据），拿它判「部分作答」，实测 9 道应拒题里 8 道被误标。
- **Agent 设计里的同一条**（`agent设计/01_核心架构.md` §4）：
  `FormatChecker.check()` 的章节完整性、参考文献完整性、三态判定都是针对**最终答案**
  定义的。中间轮次没有「## 参考文献」一节，每轮跑完整校验只会得到一堆必然违规。
  所以每轮只跑**不依赖章节结构**的证据侧子集（编号越界、数字未溯源、证据适用性），
  完整校验留到最终整合后跑一次。

**这与三·15 同族**：三·15 是「判据存在但对特定输入永远不触发」，
这一条是「判据存在且触发了，但触发得没有意义」。两者都表现为一个跑得好好的检查
给出无用信号，区别只在方向。

⚠ 推论：**判据的位置由「发现得晚还来不来得及救」决定，不由「哪里方便」决定。**
格式违规整合后修得了，放最终无妨；证据适用性（人群/终点不匹配）整合后修不了——
那时能做的只有删掉那句话，而正确动作是回去补检索——所以它必须在轮内检查。

### 三·17 同一族的第三种：不是判据没触发，是逻辑压根没执行

一·8 与三·15、三·16 说的都是**判据本身有问题**：条件太宽（恒真）、显式豁免（永不看）、
用错状态（量了也无意义）。还有一类表现完全一样、根因却不同——**代码没跑到**。

三个实例，都是「跑得好好的、什么都没报错、结果悄悄不对」：

| 现象 | 根因 | 怎么发现的 |
|---|---|---|
| 整行删除规则一条都没生效 | 早退优化写成 `if not any(p.search(全文))`，而模式是 `^…$` 锚定单行、没开 `MULTILINE` —— `search` 整份文本时 `^` 只匹配开头，于是恒判「没命中」，整个函数被跳过 | **对预期数量有感觉**：替换数只多了 1 处，而预期是二十几处 |
| 说明行没删掉，只删了它的续行 | 两组规则的执行顺序错了：子串替换先跑，把「说明：以下为**某某**…」里的称谓换掉了，随后整行模式（照原话写的）就再也匹配不上 | 看生成结果，不是看计数 |
| 结论行声称「链接全部可达」而那项根本没跑 | 检查在非 git 目录下跳过，结论行却是写死的一串文字，不问哪几项真跑过 | 在交付版目录上跑时发现输出里有「跳过」字样，而结论行照旧 |

**为什么这一类特别危险**：前两族至少会「打印一个绿」，而这一族**连打印都对**——
它输出的数字、结论、退出码全是正常的，只是背后少做了事。

**能抓住它的只有两件事**：

1. **对预期数量有感觉**。上表第一行如果不是「该是二十几处而不是 1 处」这个直觉，
   它会一直静默错下去——所有自检都会通过，因为待检的内容压根没被改动。
2. **看产物，不看计数**。上表第二行的替换计数是对的（续行确实删了），
   只有打开生成的文件才看得出主行还在。

⚠ 推论：**给检查加「本轮实际做了多少」的计数还不够，还要问「这个数是不是我预期的量级」。**
一·8 那条要求「覆盖率为 0 时判不通过」，挡得住完全没跑；挡不住「跑了但只做了 1/20」。

### 三·18 「空洞的部分作答」不能用规则解

判断「可以回答的部分」里的内容**是否回应了本题**，本质是语义匹配，不是格式校验。
实测：一道题只有 1 条带出处的句子却正中题意（问入组人数，答了 CLARITY-AD 1795 人），
另一道同样 1 条却答非所问（问 2026 年获批，答「MS 是自身免疫病」）——
**按条数、按章节都区分不开**。

这和「张冠李戴」（HFrEF 数据用来答 HFpEF，有出处、可溯源、完全合规）是同一类问题，
应当归到人群 / 终点匹配校验里一并考虑，而不是在格式校验层用规则去凑。

✅ 已解的是其中可判的那一半：**时间越界**——问题年份 > 本次证据最大年份时强制完全拒答，
纯元数据比较。⚠ 界限必须用**本次证据**的最大年份，不能用语料元数据里的 `pub_year.max`
（那是 2026，拿它当界限这一类根本判不出来）。实测 19 道题里只打中 1 道，无误伤。

### 三·19 单卡上并行调本地模型只有约 1.36×

4 线程 vs 串行实测。多个请求争同一份权重与同一块 GPU，Ollama 服务端会排队。
同一个线程池跑纯 I/O 等待任务实测 3.98×。

**「按 CPU 核数开线程」对生成不适用**，对评估 / 分词 / 正则这类纯 CPU 批量才适用。

⚠ `sum(各任务耗时) / 墙钟` **不能**用来衡量这种加速比——请求在服务端排队时，
每个任务的计时里都含着排队等待，算出来会虚高到接近线程数。

### 三·20 其余单点坑

- **LangChain 的 `RecursiveCharacterTextSplitter` 在无换行连续正文上 overlap 会塌成 0**，
  因此自研了切分函数。
- **`rank_bm25` 全驻内存，4M 放不下**，改用 `bm25s`（分数预计算进 scipy CSC，可 mmap）。
- **短正则会抢占更长的词典命中**（`cancers?` 咬住 "cancer"，挡掉 "non-small cell lung cancer"），
  改为两路取候选、按跨度长者优先裁决。
- **上下文按 `[S#]` 出处头切块要用顺序锚定，不能 `split("\n\n")`**——证据正文本身含空行。
- **筛掉证据后不要重编 `[S#]` 号**，引用映射会全部失效、复跑日志也对不上。
  代价只是编号可能不连续（`[S1][S3][S4]`），可接受。
- **byte-level BPE 的「encode→decode 往返一致」不能证明分词正确**——decode 只是拼接字节，
  任何切分都能往返。要证明 token 计数与推理端一致，只能拿 `prompt_eval_count` 对。
- **算引用准确率时必须先把参考文献一节挖掉**：那一节是代码生成的，每条开头都有 `[S#]`。
  实测 4 份真答案，**71 个编号里 22 个来自文献列表**，正文只有 49 个。
- **一处错误不要污染两个指标**：越界编号只由幻觉类管，格式类只报「本来存在却没列进文献表」的编号。
- **风险类打分不要用「除以上限再截断」**：短文本一两个信号就顶到 1.0，**失去单调性**。
  用 `1 - exp(-密度/尺度)`：恒在 [0,1) 且严格单调。
- **构造参数别和方法重名**：`self.check_numeric = bool(...)` 会直接把同名方法盖掉。
- **Markdown 标题正则里前后不能用 `\s*`**（`\s` 吃换行，会把标题后面的空行一起吞掉），
  一律用 `[ \t]*`。
- **「宽松引用编号」正则不能一条式写**：会把 `随访(24)周`、`分组(3)` 当成引用并在自动修正时删掉。
  裸数字**只认方括号**。
- **判定与修正必须共用同一套归一函数**，否则会出现「校验说缺章节、修完还是缺」的死循环。
- **整段替换某一节时先把挂在后面的引用块捞出来**：参考文献常是最后一节，
  「从标题替换到文末」会把免责声明一起删掉。
- **提示词与判分口径不一致，测出来的是自己的矛盾**：写口径时先把提示词允许的行为列一遍。
- **验证夹具要分两套**：把「元数据本来就残缺」的样本混进「合规基线」夹具，
  所有应当合规的断言会集体失败，测出来的是夹具的问题不是代码的问题。
- **`include_router` 之后遍历 `app.routes` 打印路由表会一条业务路由都看不到**
  （fastapi 0.141 / starlette 1.6 把子路由塞进一个内部对象）。改从 `app.openapi()["paths"]` 读。
- **`ORDER BY ts DESC` 在同一毫秒内不稳定**（`ts` 是 `time.time()`）：
  连续写入的几条记录时间戳完全相同，分页时同一条可能重复出现或整条漏掉。一律加 `rowid DESC` 兜底。
- **一次问答 100 秒量级的路由必须写同步 `def`，不能写 `async def`**，否则事件循环被钉死、
  连健康检查都不响应。FastAPI 会把同步路由丢进线程池，`contextvars`（request_id）
  随之复制过去——这条实测确认过，不是照着文档信的。
- **SSE 一旦开始 yield，就再也没法表达 HTTP 层的失败了**（状态行已发出）。
  并发闸门、鉴权、参数校验必须在返回流式响应**之前**做完；流开始后只能发 `error` 事件。
  同理，流式请求的耗时**中间件量不到**（它在响应头发出那刻就停表），要由流生成器自己收尾时写。
- **预热只加载检索器是不够的，必须连模型一起预热**：live 模式下**第一个 LLM 调用是中译英**，
  它自带较短超时，撞上模型冷启动就失败 → 静默降级成「不翻译」→ 检索漂 → 拒答；
  而**答案那次调用因为模型已被翻译那次装好了反而很快**，于是表面看就是
  「库里没证据、而且答得很快」。一次 `max_tokens=1` 的微型生成就能挡掉（2.44 s）。
- **追问改写会改，但常常丢主题词**：改写率 0.50→0.81、**保实体率 0.25→0.56**。
  「它们的不良反应呢？」→「这些酶替代治疗药物的不良反应是什么？」——指代解对了，
  但**丢了病名**，拿去检索就漂到别的药去了。
- **「系统知道的事没告诉人」和 bug 一样贵**：快照模式下问范围外的问题，
  服务端在选证据那一步（第 0 秒）就知道匹配不上，却要等整条链跑完二十多秒才拒答。
  两条都不是代码错，是接口没把自己已知的事说出来。
- **`argparse` 的 `default=` 会让配置文件与环境变量永远轮不到，而且不报错**：
  argparse 分不清「显式传了 `--port 8000`」和「没传所以取默认 8000」。
  写法是 **CLI 一律 `default=None`**（`store_true` 也要显式 `default=None`），
  真正的默认值只在配置对象的字段上写一份。优先级方向也别搞反：
  **CLI > 环境变量 > 配置文件 > 默认值**——配置文件说「这台机器平时怎么跑」，
  命令行说「这一次要怎么跑」。
- **`.gitignore` 不支持行尾注释**，注释必须单独一行。
- **交付包同步是单向的**：`scripts/` → 包内，永远不会反过来。
  改代码只改 `scripts/` 下那份，改包内副本会被下一次同步覆盖掉。

### 三·21 Windows 路径写进普通字符串，`\r` 会把整行吃掉

`E:\rag` 写在非 raw 的字符串或 docstring 里，`\r` 是**回车转义**，不是两个字符。
后果是打印出来的那一行被回车顶掉前半截，而**源码看着完全正常**。

实测：两个脚本的「用法」行长年写着

    用法:  python E:\rag\scripts\ask.py 你的问题写在这里

打印出来只剩 `python E:`——一条本该告诉人怎么跑的说明，两年里没跑通过一次。
同一族的还有 `\a`（响铃）、`\b`、`\f`、`\v`、`\t`，Windows 路径里 `\rag`、
`\bin`、`\app`、`\test`、`\vec` 都会中招。

**做法**：路径要么用原始字符串（`r"..."`），要么写双反斜杠，要么直接用正斜杠。
⚠ 静态检查能帮上忙但不完全：Python 3.12 起对未知转义（如 `\s`）会发
`SyntaxWarning`，但 `\r` `\b` `\t` 是**合法转义**，一声不吭。

### 三·22 写给「拿到仓库的人」看的说明，必须在干净 clone 上验

**开发机永远比 clone 多出一堆东西**：`ollama/`（模型）、`data/`（向量库、BM25、
golden 跑测明细）、`report_data/`（历史报告与验证夹具）、以及各种未跟踪的本地文件。
在开发机上验证一份「给别人看的说明」，验的是自己的环境，不是别人的。

**同一问题已经出现两次，一次在文件层、一次在文档层**：

| | 表现 | 真相 |
|---|---|---|
| ① 文件层 | 本机 224 / 99 / 66 全绿 | clone 后变 95 / 65 **加一次崩溃**——三份验证夹具在 `report_data/`，没进仓库 |
| ② 文档层 | 本机七道闸门全绿 | clone 后**只有三道跑得了**——闸门表的依赖列漏写了 Ollama 模型与 `data/golden/` |

两次都不是代码错，是**验证环境比交付环境富裕**，于是缺什么都看不见。

⚠ **本机的绿是信息量最低的那种绿。** 它只证明「在什么都齐的机器上能跑」，
而那恰恰是最不需要证明的一件事。

**方法：验证交付物要用交付物本身，不用开发环境的副本。**

具体做法是真的 `git clone` 一份到临时目录，在那份上跑，而不是看本地引用、
也不是在生成目录里跑（生成目录仍然坐在开发机上，`MEDRAG_ROOT` 一指过去，
缺的东西照样能从别处找到）。这次就是靠一次真 clone 才发现上表第 ② 行——
在生成目录里跑的时候，那两道闸门是绿的。

⚠ 推论：凡是文档里出现「不需要 X」「秒级」「开箱即跑」这类**关于环境的承诺**，
都要在干净 clone 上兑现一次。这类句子在开发机上永远是对的。
