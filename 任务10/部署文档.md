## 二、一次性准备（每台机器只做一次）

### 2.1 建文献目录与索引统计（约 45 秒）

文档管理接口与 `/qa/stats` 的知识库统计都读这两份产物，**服务不会自己算**：

```powershell
& $py E:\rag\scripts\服务_文档目录.py --build
```

产出：

| 产物 | 大小 | 内容 |
|---|---|---|
| `data\docs_catalog.db` | 1.0 GB | 2,274,167 篇文献的目录（SQLite，只读使用） |
| `data\index_stats.json` | 4 KB | 文档总数 / 块数 / 索引占盘 / 三个建库时间 / 增量更新次数 |

实测：读 `merged_4m.parquet` 0.7s → 分组 10.2s → 摘要 13.5s → 写库 11.3s → 建索引 8.4s，**合计 44.8 秒**。

> **为什么必须离线算**：同样的数字在 Chroma 上现算要 **221 秒**
> （`count(distinct pmcid)`），而且第一次 `get(where=...)` 会把进程内存顶到 **13.68 GB**。
> 放在请求路径或启动路径上都不可接受。服务启动时只是打开一个 SQLite 连接 + 读一份小 JSON。

**不建也能起服务**：问答一切正常，只是 `GET /api/v1/documents` 返 `3004`（并告诉你跑哪条命令），
`/qa/stats` 的 `index` 段 `available=false`、各计数为 `null`（**不是 0**）。

### 2.2 配置文件

```powershell
Copy-Item E:\rag\.env.example E:\rag\.env
notepad E:\rag\.env
```

`.env.example` 由 `服务_应用.py --write-env-example` 从代码里的 `ENV_FIELDS` 表生成，
**30 项全覆盖，不会和代码脱节**。`.env` 已被 `.gitignore` 排除（里面可能有 API Key）。

## 三、配置：CLI > 环境变量 > .env > 默认值

四层，**从左到右优先级递减**。

```powershell
& $py E:\rag\scripts\服务_应用.py --print-config     # 看每一项的值与它从哪一层来，不起服务
```

输出每行是 `配置项 / 生效值 / 来源(cli|env|dotenv|default) / 环境变量名`。

**为什么 CLI 必须压过 `.env`**：`.env` 表达"这台机器平时怎么跑"，命令行表达"这一次要怎么跑"。
反过来的话，`README` 与演示台本里那些 `--mode live --translate llm` 会被 `.env` 里的
`MEDRAG_MODE=snapshot` 静默吃掉——**所有复现命令集体失效，且不报错**。

常用配置（完整 30 项见 `.env.example`）：

| 环境变量 | 命令行 | 默认 | 说明 |
|---|---|---|---|
| `MEDRAG_HOST` / `MEDRAG_PORT` | `--host` / `--port` | 127.0.0.1 / 8000 | |
| `MEDRAG_MODE` | `--mode` | snapshot | `live` = 真检索，要 65GB 向量库 + 15.8GB 内存 |
| `MEDRAG_TRANSLATE` | `--translate` | dict | ⚠ live 模式问中文**务必用 `llm`**，见第七节 |
| `MEDRAG_MODEL` | `--model` | qwen3:8b | |
| `MEDRAG_BASE_URL` | `--base-url` | http://localhost:11434 | Ollama 地址 |
| `MEDRAG_MAX_CONCURRENT` | `--max-concurrent` | 2 | 单卡上并行只有约 1.36×，调大没用 |
| `MEDRAG_API_KEY` | `--api-key` | 空 | **非空即开启鉴权**（`X-API-Key` 或 `Bearer`） |
| `MEDRAG_RATE_LIMIT` | `--rate-limit` | 0 | 每分钟上限，0 = 不限 |
| `MEDRAG_DOCS_DB` | — | `data\docs_catalog.db` | 文献目录 |
| `MEDRAG_INDEX_STATS` | — | `data\index_stats.json` | 索引统计 |
| `MEDRAG_CHROMA_DIR` | — | `data\chroma_db_4m` | **只用于健康检查与占盘统计**，不在这里加载 |

⚠ `.env` **不支持行尾注释**：`MEDRAG_MODE=live  # 真检索` 会把 `# 真检索` 读进值里。
注释单独一行。（同 `.gitignore` 的老规矩。）
⚠ 值写错会**当场报错退出**，不会静默取默认值：`MEDRAG_PORT=八千` → `ConfigError`。

## 四、起服务

```powershell
# A. 开发/演示：快照证据，不加载 65GB 向量库，秒级启动
& $py E:\rag\scripts\服务_应用.py --port 8000

# B. 真检索（要 65GB 向量库 + 3.4GB BM25 索引 + 约 15.8GB 内存）
& $py E:\rag\scripts\服务_应用.py --port 8000 --mode live --warmup --translate llm

# C. 带鉴权与限流
& $py E:\rag\scripts\服务_应用.py --port 8000 --api-key 你的密钥 --rate-limit 30
```

- 交互文档 <http://127.0.0.1:8000/docs>，离线一份在 [`openapi.json`](openapi.json)
- **B 的 `--warmup` 会连模型一起预热**（约 70 秒）。不预热的话，第一次请求里的中译英
  会撞上 qwen3 冷启动而超时降级——表现是"检索漂了、还答得很快"，比报错难查得多。
- 32G 内存的机器**不要同时起两个 live 进程**（一个检索器就 15.8GB）。

不起服务也能做的事：

```powershell
& $py E:\rag\scripts\服务_应用.py --print-routes        # 18 个接口
& $py E:\rag\scripts\服务_应用.py --print-config        # 生效配置 + 每项来源
& $py E:\rag\scripts\服务_应用.py --dump-openapi        # 导出 任务10\openapi.json
& $py E:\rag\scripts\服务_应用.py --write-env-example   # 重生成 .env.example
```

## 五、健康检查与探针

| 端点 | 用途 | 会不会碰下游 |
|---|---|---|
| `GET /health` | **存活探针**（liveness） | **绝不碰**。只答"进程还在不在" |
| `GET /health/ready` | **就绪探针**（readiness） | 探 Ollama、stat 向量库与两个 SQLite |

存活探针刻意不依赖下游：一旦依赖，Ollama 抖一下就会把好好的进程重启掉。

`/health/ready` 的六个组件（任务书点名的 LLM / 向量库 / 数据库都在里面）：

| 组件 | 检查内容 | 关键依赖 |
|---|---|---|
| `llm:ollama` | 探 `/api/tags`，确认目标模型在列 | 是 |
| `vector_db` | stat `chroma_dir`（**只 stat 不打开**） | 仅 live 模式 |
| `retrieval:live` / `retrieval:snapshot` | BM25 索引目录 / 快照文件 | 是 |
| `call_log_db` | 调用记录 SQLite 可读写 | 否 |
| `session_db` | 会话 SQLite 可读写 | 否 |
| `doc_catalog` | 文献目录可用与否 + 篇数 | 否 |

任一**关键**组件不通过 → `status=down`，HTTP **503** + 业务码 **5002**；
非关键的挂了 → `status=degraded`，仍返 200（服务还能答题，只是记录/目录功能受损）。

## 六、日常运维

```powershell
# 会话按 TTL 清理（默认 30 天。服务运行期不会自动清，靠这条定时跑）
& $py E:\rag\scripts\服务_会话.py --purge-days 30

# 调用记录清理（保留最近 30 天）
& $py E:\rag\scripts\服务_日志.py --purge-days 30

# 看调用统计 / 导出调用记录
& $py E:\rag\scripts\服务_日志.py --stats
& $py E:\rag\scripts\服务_日志.py --export E:\rag\report_data\调用记录导出.txt

# 重算索引统计（换过索引、重建过库之后跑一次；不重建目录）
& $py E:\rag\scripts\服务_文档目录.py --stats

# 量一下文献目录的真实耗时（详情/列表/标题搜/COUNT）
& $py E:\rag\scripts\服务_文档目录.py --bench
```

日志滚动 10MB × 5 份，落在 `logs\service\`（`api.log` / `error.log`），**行首带 `request_id`**，
与响应体、`data\service\api_calls.db` 三处对得上。

**录屏或出统计报表前**：把 `data\service\*.db*` 与 `logs\service\*.log*` 移进各自的
`_archive\` 再重起服务（目录里已有这个惯例，是归档不是删除）。

## 七、故障排查（都是实测撞出来的）

| 现象 | 真实原因 | 处理 |
|---|---|---|
| live 模式问中文，答"根据现有文献无法回答"，而且**答得很快** | 中译英走了词典，词表外的病名药名被整段丢弃 | 加 `--translate llm`；查响应体的 `retrieval_query` 是不是还是中文 |
| 同上，但 `retrieval_query` 是中文原句 | 第一次 LLM 调用（翻译）撞上模型冷启动而超时降级 | 起服务时加 `--warmup` |
| 所有错误码都变成 5001/500 | 按路径导入的模块没登记进 `sys.modules`，异常类出现多个副本 | 已修；新写模块一律用 `_load_by_path()` |
| `GET /documents` 返 3004 | 没建文献目录 | `服务_文档目录.py --build`（45 秒） |
| `/qa/stats` 的 `index` 段全是 null | 缺 `index_stats.json` | `服务_文档目录.py --stats` |
| `/health/ready` 返 503 | 看 `detail.components` 里哪个 `critical` 组件 `ok=false` | 多半是 Ollama 没起 |
| 一次问答要一百多秒 | 正常（四段链 + 层 D 校验） | 客户端超时设到 300 秒以上；或走流式 |
| 流式很久没有第一个字 | 也正常：出处清单 0.03s 就推了，首个答案字要 7.7~8.0s | 前端先渲染 `sources` 事件 |
| 起服务报 `ConfigError` | `.env` 里某项写错（如端口写成中文） | 按报错里的键名改；`--print-config` 复核 |

## 八、资源与耗时（实测）

| 项 | 数值 |
|---|---|
| snapshot 模式常驻内存 | 数百 MB（不加载向量库） |
| live 模式检索器 | 首次加载 **67.2 秒 / 15.8 GB RSS**，之后单次检索约 0.5s |
| qwen3:8b 显存 | 6.33 GB（`num_ctx=12288`，10G 卡有余量） |
| 一次同步问答 | 34~42 秒；流式 28~41 秒 |
| 文献详情 / 列表 | 0.0 ~ 1.0 ms |
| 标题模糊搜（最坏，全表扫零命中） | 824 ms |
| `/qa/stats` | 毫秒级（知识库那段是启动时读好的快照） |
| 索引占盘合计 | **68.9 GB**（向量库 64.6 + BM25 3.3 + 文献目录 1.0） |
