## 三、错误码与异常处理

五族，前缀即家族：

| 段 | 含义 | HTTP | 例 |
|---|---|---|---|
| 1xxx | 参数与请求（调用方能自己修） | 4xx | 1001 参数错误 / 1002 缺参 / 1003 越界 / 1004 请求体非 JSON |
| 2xxx | 认证与配额 | 401/403/429 | 2001 认证失败 / 2003 无权限 / 2004 限流 |
| 3xxx | 资源 | 404/503 | 3001 资源不存在 / 3002 会话不存在 / 3004 索引未就绪 |
| 4xxx | 模型与外部依赖 | 502/503/504 | 4001 调用失败 / 4002 超时 / 4004 服务不可用 |
| 5xxx | 服务内部 | 500/503 | 5001 内部错误 / 5002 依赖不可用 / 5003 服务繁忙 |

四类异常统一收敛：

| 来源 | 转成 |
|---|---|
| 自定义 `APIError` | 对应业务码 + 码表里的 HTTP 状态 |
| pydantic 校验失败 | 1001 / 1002 / 1003 / 1004（按错误类型细分） |
| Starlette `HTTPException` | 按状态码映射（404 → 3001 等） |
| 其余任何异常 | **5001**，日志留全栈，响应体只给一句话 |

**两条刻意的设计**：

1. **拒答不是错误。** 证据不足时系统返回带固定拒答短语的结构化回答，走 HTTP 200 / code 0，
   只在 `data.refused` 标一位。把"守住知识库边界"做成 4xx，等于让阶段九花一整个阶段做出来的
   能力在接口层被表达成一次失败。拒答率单独在 `/qa/stats` 里统计。
2. **未知异常不伪装成已知码。** `classify_exception` 只对**能确定含义**的给具体码
   （`LLMError` 按消息分流成 4001/4002/4004，`sqlite3.Error` → 5004），其余一律 5001——
   把未知异常塞进一个看起来正常的 4xxx，会让线上真正的 bug 藏起来。

## 四、同步与流式

两条路径共用同一条准备流程，差别**只有输出方式**：

```
校验参数 → 关联会话（取历史、判追问、改写）→ 选证据 → 占并发名额
        → 跑流水线 → 组装 AskData → 落库（会话轮次 + 调用记录）
```

`done` 事件的载荷**就是**同步接口 `data` 的那个结构（验证里有一条专门断言两者字段集合完全
相同），客户端可以在两种模式间切换而不改解析代码。

### SSE 事件

| 事件 | 含义 |
|---|---|
| `meta` | 请求受理：request_id / session_id / 原始与改写后的问题 / 检索模式 / 链路开关 |
| `stage` | 某一段开始或结束：stage / status / elapsed / token 数 / 是否成功 |
| `sources` | 出处清单，**上下文组装完成即发出**（早于模型的第一个字） |
| `delta` | 文本增量：stage + text。**过程量** |
| `check` | 阶段九层 D 的校验与修正结果 |
| `done` | 最终结果 |
| `error` | 失败：code / message / detail，之后流即结束 |

```
t=0.02s  meta ─▶ sources（6 条出处，含 PMCID 与链接）─▶ stage(evidence_evaluator,start)
         │        ← 用户在这里就能看到"将依据这几篇文献作答"
t≈7.7s   stage(answer_generator,start) ─▶ delta ─▶ delta ─▶ …（②草稿逐字）
         ├─ stage(critical_reviewer)      ← ③审查是 JSON，一个 delta 都没有
         ├─ stage(final_assembler,start) ─▶ delta …（④定稿逐字，客户端在此清空缓冲区）
t≈33~43s check（层 D 判定）─▶ done（后处理完成的最终答案）
```
（时间取自 2026-08-10 实测的三道题；出处 0.03 s 与首字 7.7 s 差了 250 多倍，见「七 2」。）

**三个必须说清楚的点**：

- **最终答案以 `done` 为准，不是 delta 拼接的结果。** 参考文献列表、免责声明、越界编号删除、
  章节标题归一都发生在模型写完之后。验证里有一条就在断言「done 的答案 ≠ delta 拼接，且更长」——
  它证明后处理确实发生了（离线夹具里是 1114 字 vs 176 字）。
- **只有写自然语言的两段会流式**（`answer_generator` / `final_assembler`）。①③要的是完整可解析
  的 JSON，逐块转发只会让客户端看到半截对象。所以每个 `delta` 都带 `stage`，客户端在这两段的
  `stage/start` 上清空缓冲区即可。
- **①③几十秒不出一个字，中间的静默会被反向代理掐断**，所以队列空转时发 SSE 注释行 `: ping`
  （注释行不触发客户端的 message 事件）。

### 埋点方式：包一层，不改上游

阶段七、九的代码**一行没动**。三个透明代理共用一条**线程局部**的事件总线 `EmitBus`：

| 包装器 | 干什么 |
|---|---|
| `_TappedAssembler` | 组装完上下文就发 `sources` —— 流式在本系统里最实在的价值 |
| `StreamTapGenerator` | 文本段走 `/api/chat` 的 `stream:true` 逐块转发；JSON 段原样透传 |
| `TappedPipeline` | 覆写 `_run_stage` / `_run_fixer` / `postprocess`，发段落与校验事件 |

总线按线程存不是可选项：流水线是并发共享的单例，把 emit 挂成实例属性，两个并发请求会互相
串台（同步请求还会收到别人的 delta）。同一个流水线实例同时服务两种模式——**没绑总线的线程
自动走非流式**。

## 五、会话关联：历史只用来改写检索式

「它的副作用呢？」这句话拿去检索全库 399.8 万块英文文献，召回的是噪声；模型再守约束，
基于噪声证据也只能拒答。所以历史真正起作用的地方只有一个：**把追问补全成能独立检索的问题**。

| 策略 | 做什么 | 代价 |
|---|---|---|
| `none` | 不改写，历史只存不用 | 追问检索不到东西（消融对照组） |
| `concat` | 把上一轮问题拼在前面 | 零成本，但**只对检索有效**——模型看到的问题里指代仍在 |
| `llm`（默认） | 让模型重写成独立问题，检索与提问都用它 | 多一次约 2 秒的调用；失败自动降级为 `concat` |

**历史绝不进证据区。** 把上一轮问答原文拼进上下文，等于给模型一段「没有 `[S#]` 出处的事实
材料」，它会照着写——阶段九压下去的编造会从这个口子回来。验证里有一条专门断言中间结果里
不含历史原文。

**指代检测器只是个省钱的闸门，不是判决**：它说"是追问"就花一次改写调用，说"不是"就跳过。
14 条标注样例实测 **13/14**，假阴性 **0**、假阳性 **1**（"什么是随机对照试验？"——短但独立）。
两侧代价不对称，所以分开报而不是合成一个准确率：假阳性只白花 2 秒，假阴性会让检索真吃到噪声。

未知的 `session_id` 走**自动建会话**而不是报 3002：聊天类接口要求先建会话再提问是徒增一次
往返。`GET /api/v1/sessions/{id}` 上不存在就是 3002，两者不矛盾——一个是写入语义，一个是查询语义。

## 六、调用记录：日志与数据库都要

任务书说"到日志或数据库"，这里**两个都做**，因为它们回答的不是同一个问题：

- **滚动日志**回答"这一次到底发生了什么"——按 `request_id` grep，能看到进了哪几段、每段多久、
  哪一步报的错。人排障时读的是它。
- **SQLite** 回答"这一批总体怎么样"——成功率、p95 耗时、拒答率、层 D 合规率、token 花销。
  "用于后续统计"这句话意味着要能聚合，而聚合一份滚动文本是自找麻烦。

⚠ **流式请求的耗时不能靠中间件量**：中间件在响应头发出那一刻就停表了，SSE 正文还要再流
一分钟。流式的记录由流生成器自己在 `finally` 里写——并发名额也在那里释放。

⚠ 所有写入都吞异常并转成日志：**记录失败绝不能让问答失败**。写失败计数进健康检查，
不让存储故障静默。

## 九、关键设计取舍

**1. 流水线懒加载，服务先起来。** 检索器首次加载约 15.8GB RSS + 数分钟（Chroma HNSW），
模型另占 6.3GB 显存。放进 `startup` 会让服务几分钟起不来、健康探针先把它判死。
所以 `ServiceState.pipeline` 是**带锁的懒属性**：进程秒起，`/health` 立刻可用，
第一次问答才付加载代价（也可以 `--warmup` 显式预热）。

**2. 并发闸门是功能，不是保护性摆设。** 阶段八实测：单卡上并行调本地模型只有约 **1.36×**
加速，多个请求争同一份权重、Ollama 服务端排队。放开并发只会让每个请求都变慢，还可能触发
显存换出。所以有 `BoundedSemaphore(max_concurrent=2)`，排不上队就返回 **5003**，
而不是让请求在里面无限期等。

**3. 路由一律写同步 `def`，不写 `async def`。** 一次问答是 100 秒量级的阻塞调用，
写成 `async def` 会把事件循环钉死，连 `/health` 都不响应。FastAPI 对同步路由自动丢线程池，
`contextvars`（request_id）会随 `anyio.to_thread.run_sync` 复制过去——这一条**靠实测确认**
而不是相信文档（验证 D2 组）。

**4. 存活探针与就绪探针分开。** `/health` 只回答"进程在不在"，绝不碰下游——存活探针一旦
依赖下游，下游抖动就会把好好的进程重启掉。`/health/ready` 才探 Ollama 与存储。

**5. 流式必须在开流之前抢并发名额。** SSE 一旦开始 yield，状态行就已经发出去了，
再"忙"就只能是流里的一个 error 事件、HTTP 仍是 200。所以 `acquire_slot()` 在返回
`StreamingResponse` 之前调用，才能把"忙"如实表达成 503。

**6. 快照检索模式如实标注。** 默认用阶段七固化的 4 组真实检索结果（省掉 65GB 库），
但响应里必带 `retrieval_mode: "snapshot"` 与 `pool_match: exact|keyword|fallback`——
匹配不上时标 `fallback` 而**不假装匹配成功**。没人能把演示数据当成真检索。

**7. 鉴权与限流默认全关。** 单机离线场景强制鉴权只是给自己添麻烦。
`--api-key` 一开就生效（`hmac.compare_digest` 定长比较，不用 `==` 泄漏前缀）；
健康探针不走鉴权，否则探针会把服务判死。

## 十、这一阶段踩到的坑（都是实测撞出来的）

**1. 按路径导入的模块有多个副本，异常处理器会静默失配。** 这是本阶段最贵的一个坑：
`服务_问答接口` 里 `raise SessionNotFound(...)` 抛的是 `服务_错误码.py` 的 **B 副本**，
而 `@app.exception_handler(APIError)` 注册的是 **A 副本**——两者不在同一棵继承树上，
处理器匹配不上，**3002 / 4004 这些精心分好的码统统退化成 5001/500**，而且不报任何错。
docs/工程笔记.md 三·8"跨模块 `isinstance` 必然失败"这条，这次是以"错误码全变 5001"的形式出现的。
修法：所有 `_load_by_path` 一律**登记进 `sys.modules`**（先登记再 `exec_module`，
失败时从缓存里摘掉）。**发现方式**：验证 C 组一跑就抓到了——如果只手工点几下 `/docs`，
这个 bug 会一直活着，因为响应体看起来完全正常。

**2. `include_router` 的子路由不在 `app.routes` 里。** fastapi 0.141 / starlette 1.6 把它们
塞进一个内部的 `_IncludedRouter` 包装对象（连 `.routes` 属性都没有）。照着遍历
`app.routes` 打印路由表，**一条业务路由都看不到**，看起来像"路由没注册成功"。
改从 `app.openapi()["paths"]` 读——那是对外发布的真实接口面，也不依赖框架内部结构。

**3. `Enum.__hash__` 按成员名算，`int in set(ErrorCode)` 恒为假。** 
`ErrorCode(code) if int(code) in set(ErrorCode) else int(code)` 这句里，
整数与枚举成员的哈希不同，集合判定永远不成立——**登记过的码也会被当成未登记**。
改成 `try: ErrorCode(code) except ValueError`。

**4. `ORDER BY ts DESC` 在同一毫秒内不稳定。** `ts` 是 `time.time()`，连续写入的几条记录
时间戳完全相同，分页时同一条可能重复出现或整条漏掉。加 `rowid DESC` 兜底。
（验证里那条"按时间倒序"就是被这个绊倒的。）

**5. 就绪探针失败应该是 503 不是 500。** `DEPENDENCY_FAILED` 一开始映射到 500，
编排系统会把它当成代码 bug 而不是依赖抖动。改成 503。

**6. `concat` 会自我复读。** 如果调用方把本轮问题也塞进了 history，
"取最近一条用户消息"取到的就是问题自己，拼出"它的不良反应呢？ 它的不良反应呢？"。
改成跳过与当前问题相同的那条。

**7. 假生成器必须能驱动流式路径。** 一开始 `StreamTapGenerator` 写死走 HTTP，
没有 Ollama 就测不了流式。改成：内层生成器若自带 `stream_messages` 就用它，否则走 HTTP，
**两条路径共用同一个消费循环**。这不是为测试硬凑的扩展点——换生成后端只需实现一个方法。

**8. `create_app(state)` 传错位置参数，报出来的是驴唇不对马嘴的错。** 第一个位置参数是
`settings`，传成 `ServiceState` 后报 `'ServiceState' object has no attribute 'log_dir'`。
已在入口认下这种写法，不让人绕远路。

**9. 快照模式下问范围外的问题，用户要等二十几秒才知道答不了。** 服务端在**选证据那一步**
（第 0 秒）就已经知道匹配不上了，却要等整条四段链跑完，才通过一句拒答把这件事告诉用户。
这不是模型的问题，是**接口没把自己已经知道的事说出来**。已加 `GET /api/v1/qa/topics`
（带 `?probe=` 可试探某个问题会不会命中），客户端在发请求前自检并提示、让人选择要不要继续。
**发现方式**：用户实测时连着问了「发烧怎么治疗」「癌症怎么治疗」，各等 20 秒才收到拒答——
系统行为完全正确（没编造），但体验是错的。

**10. 启动参数被打进聊天框。** 用户把 `--mode live` 当成聊天命令输入，它被当成一个问题
发给了模型，白烧 18 秒。终端客户端现在拦下 `-` 开头的输入，并说明那是**起服务时**的参数。
—— 这两条都不是代码 bug，是"系统知道的事没有传达给人"，但在一个对外的接口上，
这跟 bug 的代价是一样的。

## 十二、已知局限与下一步

**局限（如实说明）**

1. **默认是快照检索模式**：证据来自阶段七固化的 4 组真实检索结果，不是每次现检索。
   本阶段所有耗时数字都是在这个模式下测的；`--mode live` 会再加上一次检索
   （以及首次 15.8GB / 数分钟的加载）。⚠ 2026-08-11 实测：live 模式下这次检索**不是 0.5 秒**，
   而是 **11~13 秒**（`--translate llm` 的整句翻译占大头），出处清单也因此从 0.03 s 推迟到
   约 9~13 s。快照模式那组数字仍然有效，但**不能拿去描述 live**。
2. **鉴权是静态 API Key，限流是单进程内存计数**。够单机离线场景用；多副本部署要换成
   共享存储的方案。2002（凭据过期）目前是预留码。
3. **客户端断开后生成不会立刻停**：SSE 断开会关掉生成器、释放并发名额，但已经发给
   Ollama 的那一段要跑完。
4. **①③两段不流式**，等待期只有 `stage` 事件与心跳（本机实测首字要 7.7~7.9 秒；
   出处清单 0.03 秒就能发出去，所以这段等待不是"白等"，但确实还没有可读的进度描述）。
5. **会话管理是"够用"版本**，不是完整模块（完整版属于第二部分）。追问改写**已在
   2026-08-11 量过一次**（见「十四」）：改写率 0.81、保实体率 0.56——**它会改，但改完常常
   丢掉主题词，检索照样漂**。"改了之后召回是不是真的更好"仍然没有端到端的数字。
6. **样本量很小**：端到端只跑了 3 个问题 × 2 条路径。**结论看方向与量级。**

**下一步**

1. **量化追问改写的收益**：用同一批多轮问题跑 `rewrite=none/concat/llm` 三组，
   看关键信息召回（阶段八的尺子）差多少。现在只知道它"会改写"，不知道它"值不值"。
2. **`--mode live` 上的一轮压测**：真检索 + 并发 2，看 p95 与显存是否稳。
3. **先把阶段九的拒答口径拆成三态**（完全拒答 / 部分作答 / 实质作答）——
   本阶段实测已经证明二值口径会让线上的 `refusal_rate` 直接失真（见「七 4」：
   一份 1782 字、带出处、判定合规的实质回答被记成了拒答）。这件事在阶段九改，服务端一行不用动。
   `citation.missing` 同理，`/qa/stats` 的口径已经接好，剩下的是攒样本。
4. **第二部分**：完整会话管理模块、文档管理接口。

## 十四、live 模式可靠性修复（2026-08-11 补）

起因：把服务切到 `--mode live` 真检索，问「法布里病有哪些酶替代治疗药物？」，
**检索回来的是蝴蝶名录和 1919 年的文章**，答案是一句"根据现有文献无法回答"。
库里有 Fabry 的文献，是**问题在路上被弄坏了**。

这类错最贵：**它和"库里真没有证据"在响应体里长得一模一样**，从答案上分辨不出来。

### 三类"理解出错"，实测各占一份

| 失败方式 | 实例 | 修法 |
|---|---|---|
| **翻译丢实体** | 「法布里病」不在词典里 → 整词丢弃 → 只剩 `treatment` 去查全库 399.8 万块 | `--translate llm` |
| **改写丢实体** | 「它们的不良反应呢？」→「这些酶替代治疗药物的…」丢了病名 → 检索到异烟肼 | 改写提示词加硬规则（部分修好） |
| **冷启动吃掉翻译** | 重起后第一条请求，翻译撞上模型冷启动超时 → 静默降级 → 拒答 | `--warmup` 连模型一起预热 |

### 改了什么

1. **`服务_应用.py` 加 `--translate {off,dict,llm}`，默认 `dict`（行为不变）**。
   在此之前服务端**没有任何办法**用模型翻译——写死走 `RetrievalPipeline` 的词典默认值。
   词典是阶段五那份几百条的手写表，词表外的中文字符**直接丢弃**。
2. **`--warmup` 现在也预热模型**（一次 `max_tokens=1` 的微型调用，实测 2.44 s）。
   原来只加载检索器。live 模式下第一个 LLM 调用是中译英，它自带较短超时，
   撞上 qwen3 冷启动就静默降级成"不翻译"；而答案那次调用因为模型已被翻译那次装好了反而很快，
   **表面看就是"库里没证据"**。
3. **把"我理解成了什么"发给客户端**：`生成_流水线.py` 把检索层的 `enhanced.core_text`
   带进 `generation_metrics`，`服务_流式.py` 新增 `_TappedRetriever`（照 `_TappedAssembler`
   的透明代理模式写），检索一完成就发一个 `stage` 事件带 `retrieval_query`——
   **不新增第八种 SSE 事件**。响应体也加了 `retrieval_query` 字段。
4. **`服务_会话.py` 改写提示词加三条硬规则**：补全必须落到具体名称、改写后必须含上一轮主题词、
   只有不含指代词才算独立完整。

### 实测（同一把尺子，改前改后各跑一次）

改写量尺：8 种追问句式 × 2 条真实会话历史 = 16 条，约 40 秒一轮。

| 指标 | 改前 | 改后 |
|---|---|---|
| 改写率（改写后 ≠ 原句） | 8/16 = 0.50 | **13/16 = 0.81** |
| **保实体率**（改写后仍含主题词） | 4/16 = 0.25 | **9/16 = 0.56** |

> 0.56 是**低估**：被判"丢实体"的里有几条换成了更具体的药名/技术名
> （`agalsidase alfa 和 agalsidase beta 分别适合什么人？`），检索照样打得中。

翻译与冷启动：

| | 修前重起后第 1 条 | 修后 |
|---|---|---|
| 检索式 | `法布里病有哪些酶替代治疗药物？证据如何？`（**中文原句**） | `Enzyme replacement therapy drugs for Fabry disease…` |
| 结果 | **拒答** | 不拒答，6 条 Fabry 文献，层 D 合规 |
| 连问 3 次 | —— | 3/3 翻译正确、3/3 不拒答 |

回归验证：**离线 160/160**（改动前后各一轮）、**`--demo` 8 步全过**、
终端客户端渲染实跑确认（`🔍 检索式` 出现在 13.17 s，**比第一个答案字早 9 秒**）。

### 还没修好的

- **改写仍会丢主题词**（0.56）。「这些药的…」「该方法的…」这两类连改都不改。
  但现在**看得见**了：客户端把检索式打在屏幕上，一眼能判断是不是漂了。
- **译文没错但检索没捞到最相关文献**：用**纯英文**问 pembrolizumab 的 RCT 证据，
  回来的是综述、没有 KEYNOTE 原文，照样拒答。这是检索层的问题，不是理解层的。
- **证据够但模型仍先写拒答短语**（阶段九 `adv-E1` 那条口径），live 模式下又见到几次。

### 1) 先量了三个数，其中一个直接改掉了字段设计

**「文档总数」不能只报一个数字。** 库里 chunk 3,998,000 条、去重后文献 **2,274,167 篇**——
但那 227 万篇**不是 227 万篇完整文献**：

| | 实测 |
|---|---|
| 每篇平均入库块数 | **1.76** |
| 每篇原文平均块数 | 28.64（中位 26） |
| 只有 1 块入库的文献 | **54.2%**（1,232,745 篇） |
| 完整入库的文献 | **0.6%**（13,866 篇） |
| 有摘要块入库的文献 | **7.7%**（175,664 篇） |

因为 4M 是从 92,432,502 块里按**块**分层抽样的，不是按文献抽的。于是：

- `total_documents` 自带 `documents_note` 写明口径是"被抽中至少一块"；
- `DocumentIn` **同时给 `total_chunks`（原文 28.6）与 `indexed_chunks`（库内 1.76）**——
  只给前者，详情页会显示"共 26 块"然后一块也列不出来；
- `abstract` 保留（任务书点名了）但**标为可选并写明 7.7% 填充率**，不假装它总是有值。

### 2) 这三个数为什么必须离线算：221 秒与 13.68 GB

真跑过，不是估的：

| 做法 | 耗时 | 副作用 |
|---|---|---|
| Chroma sqlite `count(distinct string_value) where key='pmcid'` | **221.2 s** | —— |
| Chroma sqlite `count(*) where key='pmcid'` | 25.2 s | —— |
| `collection.get(where={'pmcid': …})` **首次** | **22.0 s** | 进程 RSS 涨到 **13.68 GB** |
| 同上，之后每次 | 0.44 s | —— |
| `merged_4m.parquet` 只读 `pmcid` 一列算 distinct | **0.7 s** | 结果 **2,274,167，与第一行逐位相同** |

最后一行是整块设计的支点：`data/bm25_index_4m/index_meta.json` 的 `source` 写明 BM25 就是从
`merged_4m.parquet` 建的，行数 3,998,000 与 `collection.count()` 一致——所以这条快路
**是权威的，不是近似**。⚠ 但我没有靠"应该相等"来推断，**221 秒那趟是真跑完的**。

那个 **13.68 GB** 是第二个理由：文献详情如果走 Chroma 的 `where`，snapshot 模式
"不加载 65 GB 库"的承诺会在**第一次请求**上破掉，而且表现得最像 bug。

⚠ 顺带否掉一条更省事的做法：**不能用 `subset_4000000_s42.parquet` 建目录**。
它有 4,002,283 行 / 2,276,496 篇，比真正入库的多 4,283 块 / **2,329 篇**——
拿它建目录会凭空多出两千多篇"查得到、检索不到"的幽灵文献，而 `3001` 本该是准的。

于是：`服务_文档目录.py --build` 离线跑 **44.8 秒** → `data/docs_catalog.db`（1.0 GB）
+ `data/index_stats.json`；服务**启动时**只打开一个 SQLite 连接 + 读一份小 JSON。

### 3) 文档接口：为什么用游标不用页码，以及标题搜的真实代价

`--bench` 实测（2,274,167 行）：

| 用例 | 耗时 |
|---|---|
| 详情 `get(pmcid)` | **0.0 ms** |
| 列表 无过滤首页 / 深游标 / journal / 年份 | **0.0 ~ 1.0 ms** |
| 标题 `LIKE %CRISPR%`（命中多） | 6.0 ms |
| 标题 `LIKE %Fabry disease%`（命中少） | 57.3 ms |
| **标题 `LIKE %不存在的词%`（最坏：全表扫零命中）** | **824.2 ms** |
| `COUNT(*)` 无过滤 | 24.0 ms |
| 最坏 + `COUNT` | 1525.2 ms |

⚠ **只量命中多的那一档会得出错误结论**：`LIKE` 配 `ORDER BY pmcid LIMIT 21` 在命中多时
凑够 21 条就停，6 ms 很好看；命中少或零命中时才是真实上限 824 ms。
量到这个数之后决定**不上 FTS5**（省 200 MB 且少一层构建）——824 ms 相对一次 30~100 秒的问答
可以忽略，写进接口 description 让调用方知道即可。

分页**没有 `page` 参数**：227 万行上 `LIMIT 20 OFFSET 100000` 要先扫掉前十万行。
只提供 `cursor`（上一页最后一条的 `pmcid`），常数代价。相应地 `total` 默认 `null`，
要就显式 `with_total=true`——这也是本阶段唯一不复用 `PageModel` 的地方。

### 4) 健康检查补上了「向量库」那一格

任务书写的是「各组件健康状态（LLM、向量库、数据库）」。第一部分的五个组件里，
LLM 有、两个数据库有、BM25 目录有，**唯独 65 GB 的 Chroma 一次都没被体检过**——
`retrieval:live` 那格查的是 BM25 目录，不是向量库。

现在加了 `vector_db` 组件：**只 stat 不打开**（打开要 22 秒 + 13.7 GB），
snapshot 模式下 `critical=false`（不加载也能服务），live 模式下 `critical=true`。
另加 `doc_catalog` 组件（非关键）。共 **7 个组件**。

> ⚠ **这里原先写的是「六个 → 8 个」，是错的**（2026-08-16 录屏前实测发现）。
> `retrieval:snapshot` 与 `retrieval:live` 在代码里是两个 `comps.append`，但它们
> **互斥**——任何一次运行只出现其中一个。按名字数会多数一个。
> 实测 `/health/ready` 两种模式都是 **7 个**：`call_log_db` / `session_db` /
> `logging` / `vector_db` / `doc_catalog` / `retrieval:*` / `llm:ollama`。
> ⚠ 验证脚本按**组件名**断言（`"vector_db" in comps`），没有按数量断言，
> 所以这个笔误一直没被测出来——**按名断言是对的设计，但它不覆盖"总数"这个口径**。

### 5) 配置：CLI > 环境变量 > .env > 默认值

`.env` 解析是自己写的十几行（没引 python-dotenv），规则钉死在 `load_env_file` 的 docstring 里，
其中 **不支持行尾注释** 与 `.gitignore` 是同一个道理。

⚠ 真正容易做错的是**优先级方向**：`.env` 说"这台机器平时怎么跑"，命令行说"这一次要怎么跑"。
反过来的话，README 与演示台本里那些 `--mode live --translate llm` 会被 `.env` 里的
`MEDRAG_MODE=snapshot` 静默吃掉，**23 处复现命令集体失效且不报错**。

⚠ 实现上的坑：**argparse 的 default 必须全部改成 `None`**。留着 `default=8000` 的话，
argparse 分不清"用户显式传了 8000"和"没传取了默认"，于是每一项都算"命令行给的"，
`.env` 与环境变量**永远轮不到**——配了不生效，还不报错。真正的默认值只在
`ServiceSettings` 的字段上写一份。

`--print-config` 打印每一项的值**与它从哪一层来**；`.env.example`（30 项）由 `ENV_FIELDS`
表现生成，不会和代码脱节。⚠ 值写错当场 `ConfigError` 退出，不静默取默认。

### 6) Postman 集合：从验证脚本的真跑里导，不另写一套

`服务_验证.py --export-postman`：包一层 `RecordingClient`（继承 `TestClient`）把**真实发出的
每个请求**录下来——method / path / params / body，以及**那一轮实际观测到的** HTTP 状态与业务码，
拿它们当断言值。测试逻辑一行都没重写。

结果：**录到 55 次调用，去重后 44 条请求，覆盖 18/18 个端点（100%）**，按验证分组归类；
会话 id / 请求 id / 文献 id 这类"跑一次就变"的值被换成 `{{sessionId}}` `{{requestId}}` `{{docId}}`
集合变量，由前面的建会话、问答、列表三条请求负责写入，集合能连着跑。

⚠ **两条"导出来能跑"的规矩，都是想清楚"这条响应在别人机器上还成不成立"才补上的**：

1. **只有录到成功响应时才把 id 换成变量。** `GET /sessions/sess-abc123 → 200` 意图是
   "查一个存在的会话"，id 每轮都变，必须变量化；`GET /sessions/does-not-exist → 3002`
   意图正是"查一个不存在的"，**换成变量它就变成 200 了，这条用例的意义会被替换掉**。
2. **故意造坏的实例不录**（缺快照 / 缺目录 / 开鉴权 / 限流 / 并发闸门 / 注入会失败的生成器）。
   把"缺目录 → 3004"录进集合，拿到一台目录正常的服务上重放就是 200——**集合无故变红，
   而且看上去像接口坏了**。`make_app(record=False)` 一处标记，导出侧不用做特例判断。
   这一条把请求数从 74 降到 55、集合从 45 条降到 44 条，**端点覆盖仍是 18/18**。

**共同的原则**：断言值可以取自真跑，但前提是**那次真跑的环境可复现**。
不满足这一条的，宁可不导出，也不要导出一条注定失败的用例。

⚠ **这里发现了一个真漏**：算端点覆盖率时发现 `POST /api/v1/sessions` **从来没有被 HTTP 打到过**
——E 组验的是 `SessionStore`（进程内），G2 用的是问答时自动建会话。任务书要求"覆盖所有 API
端点"，光有 store 的测试不算。补了 4 项之后才真到 18/18。
**"所有端点都被打到"这条断言，只有在它先失败过一次之后才值得信。**

⚠ 交付时必须一起说的话：集合只覆盖走 HTTP 的那部分。223 项里有一大批是**进程内断言**
（响应模型边界、错误码表、SQLite 存储、参数校验在模型层就被拦下），没有 Postman 形态，
**集合全绿 ≠ 223 项全绿**。
