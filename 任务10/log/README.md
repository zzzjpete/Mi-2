## 三处 `request_id` 是同一个值 —— 这是"记录"这条做到位的证据

任务书要求"记录每次调用的请求ID、耗时、结果状态"。同一次调用在三个地方留痕，用同一个 ID 串起来：

1. **响应体**：`{"request_id": "req-c8438f8c", ...}`（也在响应头 `X-Request-Id`）
2. **`api.log`**：`2026-08-11 01:53:54 INFO [req-c8438f8c] medrag.qa: 同步问答完成｜1534 字…`
3. **`调用记录导出.txt`**：`req-c8438f8c  sync  ok  0  5717.9ms  1 调用  4483 入tok…`

拿任意一个 ID 在三个文件里 grep，能拼出完整故事。接口 `GET /api/v1/qa/logs/{request_id}` 也能直接查回来。

## 两个看起来像 bug、其实是正确行为的地方

**1. 流式请求在 `api.log` 里有两行，耗时差很多**

```
POST /api/v1/qa/stream → 200  1.7ms          ← 访问日志：响应头发出的时刻
流式问答完成｜1362 字｜1 次调用｜5075.5ms      ← 收尾日志：真实耗时
```

SSE 的响应头在流开始前就发出去了，中间件在那一刻停表，所以访问日志那行永远是个位数毫秒。
真实耗时由流生成器自己在收尾时写——`调用记录导出.txt` 里记的也是这个值（5075.5ms）。

**2. `拒答=是` 与 `部分=是` 是两件事，不要合起来看**

响应体里有两个布尔：`refused` **只表示完全拒答**（答案里一条带出处的实质结论都没有），
`partial` 表示**部分作答**（问题的一部分有证据、另一部分没有，第一句写的是
「现有文献仅能部分回答此问题」）。

这两个字段是 2026-08-11 拆出来的。**在此之前只有一个 `refused`，判定是"出现了拒答短语"**，
于是"正文其实答了三四条带 `[S#]` 的实质内容、只是开头挂了拒答短语"的答案会被统计成拒答——
读的人扫一眼摘要就走，看不到下面的内容。这是当时留在阶段九的账，现在结清了：
判定改由阶段九校验器出三态（完全拒答 / 部分作答 / 实质作答），
接口层**只是读它**，不自己再判一次（见 `任务9/README.md` 三 5）。

`/qa/stats` 的 `refusal_rate` 因此也只统计**完全拒答**。

## 关于这批日志的取值范围

演示用的是**快速模式**（关掉①证据评估与③批判审查，1 次模型调用）。在 live 真检索下
单次约 20~37 秒，其中检索加翻译就占 11~14 秒——**这一段在快照模式下是 0**。

完整四段链（4 次模型调用）在 live 下实测约 **58 秒**，且这一次实测里它**没有把答案做得更好**：
四段链的终稿把具体药名从核心答案里删掉了、又留下了一句"无法回答"，反而自相矛盾
（详见 `任务10/README.md` 十四节与 `任务9/README.md` 五）。所以演示默认用快速模式，
不是为了好看，是因为**四段链在这一题上的收益没有验证出来**。

证据来自 399.8 万块 PubMed `oa_comm`（覆盖 227.4 万篇）的**真实检索**（每次现查）。
默认的快照模式则是阶段七固化的 4 组真实检索结果——**不是手编的假数据**，
但只有那四个主题问得出东西。

⚠ **live 模式问中文必须加 `--translate llm`**：默认的词典直译会把词表外的病名药名
整词丢弃（问「法布里病」只剩一个 `treatment` 去查全库 399.8 万块，检索回来的是蝴蝶名录）。
这条实测记录在 `任务10/README.md` 第十四节。
